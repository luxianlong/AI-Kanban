热点线架构

一条线:全网找热点 → 写文章。主 agent 编排,不分角色,靠确定性工具兜底。

2026-08-29 · 由「答题线」改口径而来

产出是文章,不是「对某个知乎问题的回答」—— 同一个事件可以一稿多投。 知乎仍是主要分发渠道之一,但只是渠道,不再是选题的边界。

规矩写在代码里,不写在 prompt 里。上一轮 14 次选题,有 5 次靠自觉破了例 —— 5 次全部颗粒无收。所以门槛做成物理约束:代码写候选清单,agent 只能交一个序号, 不合格的题根本不出现在它的选项里。

源的可达性(2026-08-29 实测)

「不只知乎」卡在一个很具体的地方:热榜几乎全锁在登录态后面。不带 cookie 直连:

源结果含义
news.google.com/rss200唯一免登录的一手入口 —— 所以它先落地
trends.google.com/trending400geo=CN 不支持
s.weibo.com/top/summary302跳登录
weibo.com/ajax/side/hotSearch403要 cookie
zhihu.com/hot403要 cookie(所以 scout 走 Chrome)

结论:微博 / 知乎 / X 的热榜只能走 quiet_browser 那条登录态 Chrome 通道, 各写一个适配器。Google News 是唯一能用纯 HTTP 拿到的,已实现。

未定:新源的硬门槛。知乎那四个数(ID 位数 / 浏览 / 回答数 / 首答赞数) 是知乎问题特有的量纲。微博热搜有「热度值 + 榜位 + 在榜时长」,X 有「post 数 + 榜位」, 两边都没有「我还能不能排进去」这个概念 —— 那是知乎答案排序才有的东西。 硬编一组拍脑袋的数字,恰恰会毁掉 scout 存在的理由,所以留待裁定。

三道闸

  1. 引语闸门 —— 成稿里每段引号内的文字,必须是 dossier/raw/ 下某个原件的子串
  2. 红线 —— markdown 记号 / 讨要式钩子 / 器官词 / 字数
  3. 未落盘断言 —— 引号找不到原件时,给出最接近的原件片段供人工判断

跨平台带来的新纪律:外媒原话必须双语落盘。译文不可能是原文的子串, 只写译文会被引语闸门直接拦下。格式 「原文」(译:译文)。

闸门拦住过真事。某篇成稿把「PR在我们这儿就是跳动的心脏，时不时就得蹦跶一下， 不蹦就死了」中间那句删掉了,却没有给省略号 —— 等于把压缩过的话当逐字引语发。 同一句在另一篇里是完整的,所以那篇过了闸、这篇没过。差别就是一道确定性检查。

卷宗即记忆

引用了谁的原件,那份原件就该躺在自己的 raw/ 里。否则闸门连比对都做不了 —— 真出过一次:某篇的原件躺在隔壁 run 的卷宗里,闸门直接判「无法执行」,稿子卡了一天。

侦查为什么是工作流,不是一个 agent

单 agent 会漏检索模态,而且无法自我证伪。上一轮对抗核查提出 123 处更正, 拦下多个致命错误 —— 最典型的是「某人当面骂他是骗子」流传极广,唯一信源竟是被指控者本人的回忆。

两条交付路径

路径怎么走
知乎等平台人工。HTML 出来后复制粘贴,一稿可多投
公开页publish_page.py → /p/<slug>.html

发布是单向的。公开页接口匿名写、站长才能删 —— 发出去自己撤不回来。 所以 publish_page.py 默认强制过闸,不过不发。
