热点线 DDD 模型

用领域驱动设计的那套词汇,把这条流水线重新描述一遍:六个限界上下文、 五个聚合、三条不变式。

2026-08-29 · 对应 COMPANY.md 的八段流水线

这个项目本来就有一套统一语言(Ubiquitous Language)—— 卷宗、原件、闸门、分级、留痕。 这些词在代码、文档、对话里指的是同一件事,没有翻译层。DDD 里最难的那一步,这里是现成的。

三条不变式

DDD 里聚合的意义是守住不变式。这条线上真正有约束力的只有三条,每一条都有代码在守:

① 卷宗自洽

Dossier · gate.py 引语闸门

成稿里每一处引号内的文字,必须是本卷宗 raw/ 下某个原件的子串。 不是「应该有出处」,是逐字比对。外文材料因为译文不可能是原文的子串,必须原文译文同时出现。

② 候选题不可协商

Candidate · scout.py

四道门槛不过的题,根本不进 candidates.json。 agent 只能交一个 index,不能交一道题。上一轮 14 次选题破例 5 次、5 次全部颗粒无收 —— 规则没错,错在会破例,所以把它做成物理约束。

③ 发布不可逆

PublishedPage · publish_page.py

公开页接口匿名写、站长才能删 —— 发出去自己撤不回来。 所以闸门不是发布之后的检查,是发布之前的守卫;publish_page.py 默认强制过闸。

两个值得单说的建模决定

一、防腐层解释了「门槛为什么不能通用」。 知乎的问题有「浏览 / 回答数 / 首答赞数 / ID 位数」,这套量纲是知乎答案排序特有的; 微博热搜是「热度值 / 榜位 / 在榜时长」,X 是「post 数 / 榜位」—— 两边都没有「我还能不能排进去」这个概念。所以每个平台要一个自己的适配器、 自己的门槛。把知乎那四个数硬套到微博上,不是复用,是把上游的模型污染进核心域。

二、约束放在出口,不放在读模型上。 防编造的直觉做法是限制作者能看什么 —— 只给摘要、不给原件。这里反过来: 作者能看到 raw/ 下的全部原件,这是刻意的。 因为最锋利的发现恰恰诞生于把材料摊在一个上下文里的时刻(上一篇最好的一句是 「整个封面唯一被标红的是『请随意转发分享』」—— 任何抽取器都拿不到,只能靠眼睛看)。 代价由第 5 步的闸门承担:视野不设限,出口设守卫。

这个模型没有什么

  • 没有仓储层。持久化就是文件系统,runs/<id>/ 本身就是聚合的边界。 加一层 Repository 抽象只会让「卷宗即记忆」这件事变难验证。
  • 没有防腐层之外的分层。九件工具都是单文件脚本,没有 service/domain/infra 三层目录 —— 这个规模下分层的成本高于收益。
  • 没有角色对象。2026-08-29 删掉了四角色管线:分权改由确定性工具承担, 不再由「谁能调什么」承担。
