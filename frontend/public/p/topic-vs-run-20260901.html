题和 run 是两个概念

卷宗属于题,写作属于 run —— 现在它们挤在同一个目录里

2026-09-01 · 代理任务 #212 · 全部数字由脚本遍历 runs/ 产出 · 孙宇晨那组仍在侦查中,原件数按发页时刻计

你说的是对的,而且代价可以量:runs/ 一共 682 MB,其中 270 MB 是同一份卷宗的副本 —— 四成。 根因不在流程,在领域层:domain/dossier.py 把卷宗的聚合边界画在了 run 上。 这一页给证据、给根因、给一个提议,不动代码,等你拍板。

按原件重合度判定「同一个题」(重合超过一半),28 个 run 目录里有 12 个属于 4 个题。

孙宇晨那个题最典型:同一件事写了五次,每次换一个角度 —— 是不是 AI 写的 / CZ 喊话 / 为什么 CZ 能让他停 / 为什么他愿意听 CZ 的。 五次都要重新拿一份卷宗。最后那次(今天这次)我是照 SKILL 教的做的:

卷宗是跨事件复用的资产。同一个瓜下面有几十道题,侦查一次可以答很多道: 新开 run 时把上一轮的 raw/、images/、facts/ 直接 cp 过来,只补新角度。

这句话本身没错,错在它是补丁。要靠 cp -n 才能复用的资产, 说明它被放在了错误的所有者名下。而且这个补丁有代价:入库时我不得不手写一份 _PROVENANCE.md 说明哪些是复制的、怎么复原,否则 52 MB 会在 git 里存两份。

二症状 B:一个 run 里塞了好几次写作

反过来的症状,在日本那个目录里:

目录runs/20260831-日本就职冰河期/
发布过的页面14成稿 7 个地址 + 日志页 5 个 + 其他
成稿版本9article-v1 … v7 + answer.md
编辑流程2 轮旧 Python 循环 + editorial.js
审稿轮次9横跨那两轮

但那不是一次写作的九个版本。那是两次完全不同角度的写作: 先是「算账版」(KPI、役员加法、目标改期),被你在 #208 打回之后 重写成「写人版」(林恭子的发言、内阁府的漫画、五十岁未婚率)。

而日志页把它们渲染成了一页,标题写着「改稿 12 个版本 · 审稿 9 轮」。

那一页读起来像一次连贯的打磨过程。实际上中间有一次推倒重来,而页面看不出来。 你在 #212 里说「日志页应该是 run 级」——它现在其实是题级,只是名字叫 run。

三根因:聚合边界画错了

不在流程,在领域层。domain/dossier.py 开头两行:

class Dossier:
    """目录即聚合边界:runs/<run-id>/dossier/。"""

    def __init__(self, run_dir: Path | str, facts=None):
        self.run_dir = Path(run_dir).resolve()
        self.path = self.run_dir / "dossier"

卷宗这个聚合根,身份是 run。仓储端口也照着写: DossierRepository.load(run_dir)、ensure(run_dir)、 EventStore.append(run_dir, kind, ...)。

可是这个聚合自己的定义写在同一行注释里:

卷宗 —— 聚合根。一次调查的全部材料,也是 clear 之后唯一的记忆。

一次调查服务的是一个题,不是一次写作。 所以身份该是题,不是 run。这一个字的错误,往下传成了 45 处 Python 引用、 15 处工作流引用、14 个模块,以及那 928 份重复原件。

四提议的形状

topics/<题>/                     ← 题:事件本身,跨多次写作
  dossier/                        卷宗只有一份,不再 cp
    raw/ images/ facts/ flows/
  BRIEF.md  GAPS.md
  events.jsonl                    题级事件:建卷宗 · 侦查 · 取原件 · 落事实
  runs/
    <角度>/                       ← run:一次写作,一个角度
      angle.md                    这一轮要回答的问题(现在没有这个文件)
      answer.md
      review/  round-*.json  article-v*.md
      images.plan.json  blocks.json
      events.jsonl                run 级事件:选角度 · 写稿 · 审稿 · 改稿 · 发布
      run-log.html                日志页在这一层

三条规则:

一卷宗属于题。新角度直接读上级目录,不再复制。 那 270 MB 冗余和 _PROVENANCE.md 这类说明文件一起消失。
二事件流分两层。侦查取证是题级的(做一次,几个角度共享); 写稿审稿发布是 run 级的(每个角度各一份)。现在全挤在一个 events.jsonl 里,日本那个文件有 14 条 page.published, 分不出哪条属于哪一版。
三日志页 run 级。渲染这一次写作的全过程; 卷宗那几节(侦查 / 取原件 / 落事实 / 成档)引用题级的那一份,不重复渲染。 你这句本来就是对的,只是现在的目录结构做不到。

六要你拍板

1. 做不做? 这是领域层的改动,牵动 14 个模块。收益是 270 MB 冗余消失、日志页能真的按 run 分开、 新角度不用再 cp。代价是一次不小的重构,而且期间流水线要能继续跑。
2. 分几步? 我的建议是三步走,每步一个 PR:①先加题级目录和 Topic 聚合,新 run 走新路,老目录不动; ②日志页改成读题级卷宗 + run 级写作;③再迁移历史目录。 第一步就能止住新增的冗余。
3. 迁不迁历史? 28 个目录合成约 20 个题,能脚本化,但会改动大量已提交的路径。 也可以只做新的、历史保持原样。
