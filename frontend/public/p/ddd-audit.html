1. 怎么审的

两条硬约束写进提示词:必须实际读文件,证据字段填真实代码片段; 禁止「建议再抽象一层」这类风格建议 —— 这个项目约 2000 行,为分层而分层已被否决三次, 每区最多 3 条,空数组是完全可接受的答案。核查阶段默认每条判假,必须自己打开文件才判真。

2. 最要紧的那一条

分级红线在代码里从来没有强制点

Dossier.forbidden() 只看 usable_in_draft,完全不看 grade; 而同一个内核里的 FactGrade.writable 与 Fact.quotable —— 那两个专门用来表达「【网】【传】不得进成稿」的属性 —— 全项目零调用。

实测数据:Dossier.facts() 能读到的事实里, 【网】112 条 +【传】16 条标着 usable_in_draft: true, 其中 61 条带原话。旧实现一条都拦不住 —— 未证实传闻可以被逐字引进成稿并过闸。

- return [f for f in self.facts() if not f.usable_in_draft and f.verbatim]
+ return [f for f in self.facts() if f.verbatim and not f.quotable]

构造验证:把一条【网】级原话追加进成稿,新实现当场报出并标明分级,旧实现放行。 单个卷宗的禁写清单从 18 条涨到 40 条。

值得注意的是,这个漏洞在项目自己的 冷启动实测.md 里已经被点名过 ——「不得写入成稿这条红线在代码里完全没有强制点」。后来内核补上了 writable, 却没有任何一处调用它。加了表达能力,没接上使用点,等于没加。

4. 这次审计真正说明的事

十六条里没有一条是「架构不够 DDD」。全部是具体的错误行为: 该拦的没拦、该显示的没显示、注释宣称的与代码做的相反、路径指向不存在的文件。

而其中至少五条,是前几轮重构自己制造或遗留的 —— 加了 writable 却零调用、加了 --sweep 却让无参数崩溃、 搬了目录却留下二十处旧路径。重构本身会产生缺陷,这就是为什么审计要独立于重构。

还有一个反复出现的形状值得单独记:「文档宣称的」与「代码做的」不一致。 gate 的 docstring 说不许发(实际恒放行)、说三道闸(实际四条)、说 tools 路径(实际已搬); publish_page 的注释说「提醒仍然保留」(实际一条不显示); render 的页眉说「逐字核对原件」(实际从不核对)。 这不是文档年久失修 —— 是每一次改行为时都没有同步改声明, 而声明恰恰是下一个人(或下一个 agent)唯一会读的东西。
