模型之外的那一圈：2026 年 AI Engineering Stack 十大问题的纵深解剖

摘要　2026 年的 AI 工程栈没有任何一层被公认「已解决」：在「哪一层是你最大挑战」的单选题上，答案高度分散（评估 20%、编排 18%、成本 16%、安全 15%、模型质量 10%、上下文/检索 9%、可观测性 8%），只有 4% 回答「运转良好」。本文以「问题」为纵深单元，逐一走完 现象 → 证据校正 → 病因 → 机制 → 判据 → 耦合 六步，试图论证一个统一命题：十个问题不是十件事，而是同一个结构性事实的十个切面——栈的核心是一个概率组件，而交付要求是确定性保证。本文同时对若干流传较广的数据做了反向校正，其中三条（成本机制、平台层缺失、可观测性缺失）的结论方向需要修改，一条（MCP 安全）的核心证据需要整体更换。

0　导论：方法、证据等级与统一理论

0.1　证据基础与其局限

本文主证据来自 Notion × Amplify Partners × Vercel《2026 AI Engineering Survey》（1,053 份，2026-05-16 至 06-15）。必须前置声明三条方法论限制，它们影响后文第 1、2、3、4、9、10 章的读法：

  1. 自选样本。受访者由三家公司自有渠道招募，Founder/CTO 23%、AI Engineer 19%，创业公司与早期团队严重过采样，大型企业 IT、金融/医疗等受监管行业近乎缺席。
  2. 分母不统一。原页面自述「百分比为回答者占比，分母因题而异，多选题总和超 100%」。因此「评估 20% vs 可观测性 8%」不是同口径横向比较，而是同一道单选「最大挑战」题的排名分布。8% 只意味着「很少被排在第一位」，不能推出「被低估」。
  3. 经验偏差。受访者中大量是 AI 领域新手（即便软件经验十年以上者，AI/ML 经验占比也极低）。部分「最大挑战」答案反映的是经验不足，而非工具链缺失。

为避免把问卷感受当作产业事实，本文对每条关键论断标注证据等级：

等级含义典型来源
A可复现的实测/遥测数字Anthropic 工程遥测、METR RCT、基准评测
B大样本调查的客观事实题调查中「是否具备写权限」类问题
C主观感受题 / 态度分布「感到技能退化」「认为会带来技术负债」

C 级证据是组织信号，不是工程结论；本文明确禁止用 C 级证据支撑因果主张。

0.2　统一理论：在概率组件外面套一层确定性外壳

十个问题分散在七层，但拆开后只剩一个结构性命题。2026 年的工程共识不是把概率组件变成确定的，而是在它外面套一圈确定性外壳。这圈外壳由四个原语构成，缺哪个就出现哪类问题：

原语含义缺位时表现为
可观测 Trace[1][1]　可观测 Trace 的承载物OTLP 协议 + OTel SDK；schema 用 open-telemetry/semantic-conventions-genai（2026-06-12 随 semconv v1.42.0 从主仓库拆出独立成库，含 model / agent spans、metrics、events、MCP 专用约定、provider 约定）。关键现状：所有 gen_ai.* 属性仍标 Development，无 Stable，独立仓库尚无 tagged release → 生产上实际靠桥接层：OpenInference（Arize）、OpenLLMetry（Traceloop）。OpenTelemetry / CNCF每次 prompt / 工具调用 / 中间结果可回放问题 8、1
可测量 Eval[2][2]　可测量 Eval 的承载物pytest + Inspect AI（UK AISI）、promptfoo、DeepEval（Confident AI）、Braintrust Eval()、Ragas、lm-evaluation-harness（EleutherAI）、SWE-bench harness（Jimenez & Yang, Princeton）。UK AISI / EleutherAI / Princeton NLP / Confident AI把 trace 变成分数与判据问题 1、9
可约束 Containment[3][3]　可约束 Containment 的承载物内核原语：seccomp-bpf、Landlock LSM（Mickaël Salaün）、bubblewrap（Alexander Larsson / Flatpak）、macOS Seatbelt sandbox-exec；虚拟化：gVisor（Google）、Firecracker（AWS，Rust 约 5 万行 vs QEMU 约 140 万行 C）、Kata；JS 隔离：V8 isolate（Cloudflare workerd）；WASM：Wasmtime / WASI（Bytecode Alliance）。Linux 内核 / Google / AWS / Cloudflare / Bytecode Alliance环境层硬边界，而非提示词里的软约定问题 4、5
可恢复 Durability[4][4]　可恢复 Durability 的承载物持久化执行引擎：Temporal、Restate、DBOS（Postgres 内）、Inngest、Cloudflare Durable Objects + Workflows、AWS Step Functions；理论原型是 event sourcing（Greg Young）与 WAL。Temporal / Restate / DBOS / Cloudflare / AWS状态外置、断点续跑、可回滚问题 2、6、7

成本（问题 3）与组织（问题 10）不是第五、第六个原语：成本是前四者的代价函数，组织是既有瓶颈被 AI 放大后的显影。

总纲一句话：概率的归模型，确定的归系统；模型层只能改变「倾向」，环境层才能改变「可能」。[5][5]　这句话的工程学名「确定的归系统」在学术上叫 information flow control（Denning 格模型, 1976）与 object-capability security（Mark Miller）；现代载体是 seL4、CHERI（剑桥 / Arm Morello）、Fuchsia。Denning / Mark Miller / 剑桥大学 / Google

0.3　总收益锚点

为什么值得做这一圈？McKinsey《State of AI 2026》（2026-08-25，1,719 份）显示 80% 的组织报告个体生产力提升，但只有 37% 能归因出 EBIT 影响。DORA《ROI of AI-assisted Software Development》（2026）的示范模型更直白：首年总价值 $11,646,000，但变更失败率由 5% 升至 6%，仅宕机一项就抵掉 -$344,000。这道 80%→37% 的落差，几乎全部发生在模型之外的那一圈。

1　评估（Evals）：缺的不是工具，是判据

现象（B/C）　评估被 20% 的人列为最大挑战，排名第一。但真正用于改进行为的手段仍是改 prompt（80%），其后是工具调用调优 59%、RAG 49%，微调仅 26%。生产环境 56% 监控「质量/任务成功率」。

校正　「改 prompt 是主流」不等于「evals 缺位」——它同样可以解释为 prompt 是最高杠杆、最低成本的修正手段，是理性选择而非失职。Langfuse / LangSmith / Braintrust / Arize Phoenix 均已提供 LLM-as-judge 与 CI eval gate，工具成熟度很高。真正的短板是标注过的真实任务数据集与「什么算对」的定义权。本章标题因此应读作「评估数据与标准缺位」。

病因　只有执行器，没有测量器。回归由客户发现，而非由系统发现。

机制　评估不是测试套件，是一套测量系统；它的入口不是写断言，而是误差分析。Husain / Shankar 的四步定式（源自质性研究方法论）[6][6]　开放编码 / 轴向编码 / 理论饱和直接搬自扎根理论（Glaser & Strauss；Strauss & Corbin），工具原型是 NVivo / ATLAS.ti。AI 侧的落地形态不是平台，是 notebook：pandas + Jupyter + 一张 Google Sheet / Airtable。专用标注器：Argilla（Hugging Face）、Label Studio（HumanSignal）、Prodigy（Explosion）。Shankar 的 EvalGen / SPADE / DocETL（UC Berkeley EPIC Lab, Aditya Parameswaran）把「人标 30 条 → 对齐 judge」做成了算法。Hamel Husain & Shreya Shankar 课程；UC Berkeley EPIC Lab：

  1. 建数据集：收集代表性 trace，无数据则先造合成数据；
  2. 开放编码：领域专家像写日记一样自由记录问题，先自标 30 条再让 agent 提建议；只记录第一个失败（上游错误造成下游连锁）；
  3. 轴向编码：把笔记归并成失败类别并计数——这是最关键的一步；
  4. 迭代至理论饱和：新审阅不再产生新失败模式为止；100 条多样 trace 是合理护栏。

在此之上有三件必须分开的事：

  • 三类 grader：代码型[7][7]　代码型 grader 的实现pytest/unittest、fail-to-pass / pass-to-pass（SWE-bench 的判据原语）、ruff/mypy/tsc（类型系统即免费 grader）、JSON Schema + Pydantic 校验工具调用参数、transcript 分析用 OTel span 属性。Princeton NLP；Astral（ruff）；Pydantic（Samuel Colvin）（字符串匹配、fail-to-pass/pass-to-pass、静态分析、工具调用参数校验、轮数/token 的 transcript 分析）快、廉、可复现但对合法变体脆弱；模型型[8][8]　模型型 grader / 成对比较LLM-as-judge：G-Eval、MT-Bench 与 Arena 式 pairwise（Zheng et al., LMSYS / UC Berkeley）；产品化在 Braintrust、Langfuse、Phoenix、W&B Weave 内置 scorer。LMSYS / UC Berkeley（rubric、自然语言断言、成对比较、多 judge 共识）；人工兜底与校准。
  • 能力评估 vs 回归评估：能力评估起始通过率要低（给团队一座山爬），回归评估应接近 100%。能力评估爬到高分后「毕业」为回归套件[9][9]　「毕业」在软件工程里早有名字characterization test（Michael Feathers）、snapshot testing（Jest, Meta）。工程实现＝把通过的 case 冻进 CI dataset。Michael Feathers；Meta（Jest）。
  • 双回路[10][10]　CI 与生产双回路GitHub Actions + promptfoo / pytest（本地跑、prompt 不出机器）；生产侧 Braintrust + Langfuse（现属 ClickHouse 体系）。2026 的事实配对是 DeepEval 做 CI + Braintrust 做生产追溯。promptfoo / Braintrust / Langfuse / Confident AI：CI 内跑小而精、偏确定性断言的数据集；生产侧异步采样 trace、用无参考 judge，并跟踪置信区间——下界跌破阈值才告警[11][11]　置信区间下界告警的算法scipy.stats.bootstrap / Wilson score interval；在 CI 里当成 SLO 而非断言。Langfuse / Braintrust 的 online eval + 采样做生产回路。SciPy；Langfuse / Braintrust。生产发现的新失败沉淀回 CI。

数据量分级：误差发现 100 条（自标前 30）；每个失败模式验证 evaluator 需 100–200 条标注；回归集常在 100+。

判据　能说出「上周新增了哪三个失败类别、各占多少比例」，而不是「我们的评分是 8.4 分」。

收益与耦合　三重：改动可判定；敢换便宜模型（没有 eval 就不敢降配，第 3 章的成本收益无法兑现）；回归前移。评估层是其余九项的前置条件——它排第一不是因为最痛，而是因为它解锁别的。

2　编排与 Agent 可靠性：不是智力问题，是换班制问题

现象（B）　Agent 使用率近乎翻倍，失败模式却很基础：幻觉 61%、任务中途丢上下文 47%、推理逻辑差 37%、缺少合适工具 30%、需人工紧盯 27%。

校正　「幻觉 61%」是模型层问题，不是编排层问题，把它计入编排人为放大了本层权重。真正属于编排层的是「丢上下文 47%」与「缺工具 30%」。此外「框架只解决感知–推理–行动循环」这句在 2026 年已不完全准确（见第 6 章）。

病因　大多数团队有框架，没有 harness。框架实现的是循环本身；循环之外的东西才是 harness 的职责。

机制

理论一：先判定 workflow 还是 agent。[12][12]　workflow vs agent 的边界这是显式状态图 vs 自由循环的选择：LangGraph StateGraph（边预先声明＝workflow）对 ReAct 式循环（Yao et al.）。框架谱系：Claude Agent SDK（Anthropic）、OpenAI Agents SDK、Pydantic AI、Google ADK、Microsoft Agent Framework（AutoGen + Semantic Kernel 合并）、Mastra、CrewAI。LangChain / Anthropic / OpenAI / Google / Microsoft 路径可预先编码的用 workflow（可预测、一致）；需模型自主决定路径的才用 agent。许多应用「单次调用 + 检索 + 少样本」就够。用 agent 意味着主动拿延迟与成本换任务表现，这笔交易要明说。

理论二：长任务失败是「换班制」失败。[13][13]　「换班制」的工业名字：durable execution2026 四家：Temporal（复杂长生命周期、要有人专职维护；Fateev & Abbas，Uber Cadence 血统）、Restate（同等保证、基础设施轻得多）、DBOS（状态全放 Postgres，装库不装集群，@workflow 装饰器自动持久化；Stonebraker 血统）、Inngest。边缘侧：Cloudflare Durable Objects（单实例强一致）+ Workflows。Temporal / Restate / DBOS / Inngest / Cloudflare Agent 在离散 session 中工作，每个新 session 没有前一班的记忆。实测中即便有 compaction，长循环仍呈两个固定失败模式：一次想做太多、过早认为完成。对应的 harness 四件套（A 级实测）：

  1. 初始化 agent 用不同的 prompt：第一个 context window 专职搭环境，产出 200+ 条特性需求[14][14]　「200+ 条初始 failing 的特性需求」形式上等价于 executable specification / BDD（Cucumber, Dan North），只是消费者从人换成了 agent。Dan North / Cucumber，逐条形如「用户能新建对话、输入问题、回车、看到回复」，全部初始标记为 failing；
  2. 一次只做一个 feature——根治「做太多」；
  3. 每步留干净状态[15][15]　git 就是 agent 的 undo 栈并行 agent 用 git worktree 隔离；更激进的是 jj（Martin von Zweigbergk, Google）与 container-use（Dagger, Solomon Hykes）。Google / Dagger：描述性 git commit + progress 文件，使模型可 revert 坏改动、无需猜测还原现场；
  4. 强制验证[16][16]　强制验证的判据来源测试即判据：pytest + fail-to-pass；property-based testing（Hypothesis, David MacIver；源头 QuickCheck, Claessen & Hughes）用来对付「合法变体」；编译器 / 类型检查是最便宜的不可辩驳 grader。Hypothesis / QuickCheck：用测试判定 failing→passing，而非让模型自报完成——根治「过早收工」。

理论三：多 agent 的收益来自 token 容量。[17][17]　多 agent 扇出与蒸馏回传的原语并发原语：Python asyncio/anyio、Ray（Anyscale / UC Berkeley RISELab）做进程级扇出；蒸馏回传靠 structured outputs（JSON Schema / Pydantic 约束解码），保证子 agent 只能回 1–2k token 的结构。Anyscale / UC Berkeley RISELab；Pydantic 在 BrowseComp 上三个因素解释 95% 性能方差，单是 token 用量就解释 80%，另两个是工具调用次数与模型选择。lead + subagent 的本质是给并行推理加容量：subagent 烧数万 token 探索，只回传 1000–2000 token 的蒸馏摘要。

理论四：agent 有状态且错误复利。[18][18]　错误复利与「不吞异常」传统侧：tenacity 指数退避、circuit breaker（Michael Nygard, Release It!）、Envoy retry budget；agent 侧的新做法是不吞异常——stderr 原样进上下文。Michael Nygard；Envoy 不能从头重启（昂贵且伤用户），必须持久化执行 + 从出错点恢复；把「这个工具在报错」直接告诉模型让其自适应，效果出奇地好。

判据　失败能归到具体步骤而非「整体不稳」；单 session 内 feature 完成数 ≤ 1；每步有可回滚 commit。

收益与耦合　DORA 观测到 AI 采用与交付稳定性下降 7.2%、吞吐下降 1.5% 相关。把可靠性拉回来，等于把那 -$344,000 的宕机项翻正，并砍掉 27% 案例中「需要人一直盯着」的隐性人力成本——这部分从不进预算，却吃掉了全部速度收益。

3　成本：价格在跌，消耗在涨——本文最需要修正的一条

现象（B）　76% 的团队会因成本调整 AI 用法，其中 40% 表示成本经常性压缩他们的野心。成本已是生产第二大监控项（48%），仅次于质量。

校正（结论对，机制写反）　流行叙事把账单上涨归因于「模型能力提升趋缓而价格上行」。这与事实相反：公开数据显示混合 token 单价从 2025 Q1 的 $18.40/M 降至 2026 Q1 的 $6.07/M，同比下跌约 67%；更长周期看，前沿模型每百万 token 从 2020 年的 $60 量级跌到 2025 年的 $0.05 量级。真实机制是：单价下跌，但每任务 token 消耗涨得更快——agentic 循环、重试、检索、多轮工具调用。

这个区别有硬性实操后果：若以为是涨价，你会去谈合同；若知道是消耗量，你该做的是路由、缓存、上下文预算和重试上限。

病因　按「每 token 单价」做决策是错的抽象层级。

机制　成本是架构的函数，不是价格的函数。基准事实（A）：agent 约为 chat 的 4 倍 token，multi-agent 约 15 倍；而 token 用量又是性能的主导解释变量（第 2 章）。因此正确命题不是「省 token」，而是把 token 花在有边际收益的位置，把没有边际收益的 token 彻底移出上下文。四个数量级不同的杠杆，按收益排序：

  1. 让中间结果不进上下文[19][19]　Code Mode：把工具调用编译成沙箱内代码模型只拿到一个 codemode({code}) 工具，代码在沙箱 V8 isolate 里跑，MCP 服务器被编译成 TypeScript SDK。Cloudflare 2026-04 发布的 Code Mode MCP server 把 2,500+ 端点从 117 万 token 压到约 1,000 token（-99.9%），只暴露 search() 与 execute() 两个工具，沙箱完全断网、唯一出口是 MCP 绑定。学术前身 CodeAct（Wang et al.），开源实现 smolagents（Hugging Face）。Cloudflare（Kenton Varda / workerd 血统）；Hugging Face——用代码执行包住 MCP。实测同一任务从 150,000 token 降至 2,000 token，省 98.7%：工具变成代码中可调用的函数，过滤、切片、聚合都在执行环境内完成，只回传结论。
  2. 让工具定义不全量进上下文[20][20]　按需发现工具的实现Anthropic Tool Search Tool；通用做法＝对工具 spec 做 RAG（embedding + 检索）+ MCP 的 tools/list_changed 通知做动态增删；学术侧 MemTool。Anthropic；MCP 规范——Tool Search 按需发现工具：token 降 85%，且准确率同时上升（Opus 4 49%→74%，Opus 4.5 79.5%→88.1%）。
  3. 程序化工具调用：复杂研究任务平均 43,588 → 27,297 token（-37%），内部知识检索 25.6%→28.5%，GIA 46.5%→51.2%。成本与质量在此同向，不是权衡。

4　写权限护栏：人工审批不是控制手段，是疲劳函数

现象（B，本文证据最强的一条）　能写数据的 agent 从去年的 52% 涨到 90%；权限分布为只读 10%、人在环写入 65%、完全自主 25%。控制手段：人工审批 73%、访问控制 60%，其后规划步骤 48%、检索接地 47%、记忆 47%——基本是「什么都在试」，无共识意味着无最佳实践可抄。

校正　说这些手段「极为初级」略显苛刻：65% 人在环 + 73% 人工审批本身是有效护栏[24][24]　人在环审批仍要保留的接口LangGraph interrupt()、Temporal signal、Slack 审批 bot。但设计目标是把弹窗数降到人还愿意读——这正是沙箱使弹窗减少 84% 的意义。LangChain / Temporal，在权限治理成熟之前是合理过渡态。真正的风险是它不可规模化，而不是它无效。

病因　人工审批的失效有实测数字：遥测显示用户批准了约 93% 的权限弹窗，且看到的弹窗越多、每个看得越不认真（A）。上了 OS 级沙箱（macOS Seatbelt / Linux bubblewrap，默认禁网、workspace 内可写）[25][25]　OS 级沙箱的具体原语macOS sandbox-exec + Seatbelt profile（TinyScheme 语法）；Linux bubblewrap + seccomp-bpf + Landlock LSM（非特权进程自我降权，是这条最贴切的内核原语）；Windows AppContainer + Job Object。Anthropic 已把这套开源为 @anthropic-ai/sandbox-runtime。Anthropic；Linux 内核后弹窗减少 84%。自动审批模式能拦住约 83% 的过激行为，代价是误拦 0.4% 的良性命令、仍有约 17% 漏过——它是纵深防御的一层，不是沙箱的替代品。

Agents Rule of Two[26][26]　Rule of Two 目前怎么被执行目前没有通用运行时能自动执行它，工业实现是把三元组写成能力清单 + CI 策略检查：OPA/Rego（Styra, Torin Sandall）、AWS Cedar（策略语言，形式化验证过）、OpenFGA（Auth0/Okta，Google Zanzibar 血统）、SpiceDB（AuthZed）做 PDP，返回确定性 Permit/Deny。Meta（规则）；Chrome Security Team（Rule of 2 原型）；Simon Willison（lethal trifecta）（Meta，2025-10-31；融合 Willison 的 lethal trifecta 与 Chrome 的 Rule of 2）——在鲁棒性研究能可靠检测并拒绝注入之前，同一 session 内 agent 最多满足以下三项中的两项：

  • [A] 可处理不可信输入
  • [B] 可访问敏感系统或私有数据

判据　「每个 agent 的爆炸半径能用一句话说清」；高风险动作的人工审批占比随规模下降而非上升。

收益与耦合　风险面：2026 年多份调查显示 54%–65% 的组织已发生或疑似发生 AI agent 相关安全事件（CSA 2026-01，418 份；Gravitee 2026）；有最小权限与可撤销操作后，事件从「事故」降级为「被拦截的尝试」。效率面：把低风险动作策略化放行、只对高风险留人，才能从「人在环 65%」安全地走向更高自主度，而不是靠胆量。

5　MCP：结论方向对，证据需要整体更换

现象（B）　MCP 已是事实标准（月下载 9,700 万+、10,000+ 活跃公共 server，2025 年 12 月捐给 Linux 基金会），但生产采用率不高，首要阻塞是安全。

校正（本文最重要的一次证据更换）　流传版本中的三处硬伤：

  • 「2026 年 1–2 月 30+ CVE，其中 RCE 漏洞 CVSS 9.6、影响 43.7 万+ 环境」——时间与口径都错。 CVSS 9.6 那个是 mcp-remote 的 CVE-2025-6514，JFrog 于 2025 年 7 月披露，不是 2026 年初；「43.7 万」是该 npm 包的下载量，不是受影响环境数。把去年的旗舰漏洞搬进今年当新证据，会明显夸大当前紧迫度。「30+/两个月」缺可核实出处，另一份统计给出 2026 Q3 累计 14 个 CVE。
  • 「30%–82% 存在可利用缺陷」是拼凑区间。 原始数据是：对 2,614 个公开 MCP 实现的扫描中，82% 的文件操作存在路径穿越风险，超过 1/3 存在命令注入风险。「具备风险模式」 ≠ 「可利用」。
  • 「约 1/4 完全没有认证」偏高。 实测是 2,614 个中 492 个零认证（约 19%）。更有说服力的数字其实是：约 92% 未使用规范的 OAuth；以及只有约 23% 的组织有正式的 AI agent 身份策略、14.4% 的 agent 带完整安全批准进入生产。

「MCP 是架构级风险」这个判断成立，但支撑它的证据必须全部换成上述口径清晰的版本。

病因　把 MCP 当「集成层」审计，用的是依赖管理的心智模型。任何给到 agent 的外部资源同时携带两种风险：传统供应链意义上的代码执行风险[30][30]　供应链侧的既有工具链Sigstore / cosign 签名、SLSA provenance、npm provenance attestation、SBOM（CycloneDX 已有 ML-BOM 扩展）、lockfile pinning。OpenSSF / CycloneDX，以及 prompt 注入向量。传统依赖审计（锁版本、验签名、读源码）只覆盖前者——「通过了恶意软件检查的 GitHub connector，照样能把一个被投毒的 README 直接送进模型上下文。审计过的连接器 ≠ 审计过的数据。」[31][31]　MCP 网关与扫描器的三类供给①网络允许清单/控制面；②MCP 网关（Docker MCP Gateway + MCP Catalog、agentgateway、MintMCP、Runlayer、Stacklok ToolHive）；③运行时检查器（mcp-scan / Invariant Labs、AgentAuditKit、OWASP MCP Top 10）。现实基线很差：2,303 个公开 MCP 配置中 0 个提供 RFC 9728 发现，52.1% 的远程 server 无认证，内联认证配置 100% 硬编码静态凭据，学术研究测得约 5.5% 的 server 存在 tool poisoning。Docker；Invariant Labs（已归 Snyk）；Solo.io

机制　四条来自 2026 年一手事故复盘的结构性结论：

  1. 远程 vs 本地比想象中重要[32][32]　协议层已经做的修法MCP 2025-06-18 修订起 RFC 8707 Resource Indicators 强制（token 绑定单一 server，不再是可被任意资源接受的 bearer）、RFC 9728 Protected Resource Metadata 发现、RFC 9207 iss 校验、OAuth 2.1 + PKCE。治理层：MCP 与 A2A 于 2025-12 同归 Linux Foundation 旗下 Agentic AI Foundation。Anthropic → Linux Foundation AAIF。本地工具可读源码、可 pin 版本；远程 MCP / 云连接器可以在你批准之后任意改变行为——安装时的信任决策已失效。目录外的一律按不可信处理，先用假数据在可控爆炸半径内跑。
  2. 允许清单是「能力授予」，不是「目的地过滤」。真实事故：出口白名单正确放行了产品必需的 api.anthropic.com，攻击者在挂载工作区放了一个带隐藏指令与攻击者自己的 API key 的文件，模型读取其他文件并用那把 key 调用 Files API——沙箱完美工作，数据照样外泄。白名单上任何域名可达的每一个功能都是攻击面。修法是在信任边界内侧放防御性 MITM 代理，只放行携带本 VM 自有 session token 的请求，并拦掉会触发服务端 fetch 的 header（代理必须在 VM 内，因为只有 VM 知道 provenance）。
  3. 工具返回值本身是攻击面，必须在进入上下文前在线检查[33][33]　在线检查用什么模型小而快的分类器：Meta Prompt Guard 2（86M/22M，可当 inline 过滤）、Lakera Guard（亚 50ms）、NVIDIA NeMo Guardrails、Guardrails AI、Microsoft Prompt Shields + Spotlighting（delimiting / datamarking / encoding，Hines et al.）、PromptArmor。基准：AgentDojo（ETH Zurich, Debenedetti et al.）。Meta / Lakera / NVIDIA / Microsoft / ETH Zurich。理由极重要：一旦被投毒的返回把 agent 引向外传，日志里只剩一次成功的、已授权的 API 调用，事后毫无信号可查。做检查的分类器可以是小而快的模型。
  4. 凭据永不进入沙箱[34][34]　凭据隔离的具体做法HashiCorp Vault / AWS Secrets Manager / 1Password Service Accounts 存 token；OAuth Token Exchange（RFC 8693）换窄作用域短时 token；git 侧＝初始化时用仓库 token clone 后接本地 remote，agent 全程不碰 token；工具侧＝OAuth token 存 vault、经专用代理注入。HashiCorp / AWS / 1Password；Anthropic（Managed Agents 模式）。git 用仓库 token 在沙箱初始化时 clone 并接进本地 remote，此后 push/pull 正常而 agent 从未碰过 token；自定义工具走 MCP，OAuth token 存 vault，模型经专用代理调用，harness 自己也不知道任何凭据。原因是「窄作用域 token」这一缓解措施隐含「模型拿有限 token 做不了什么」的假设，而该假设会随模型变强而过期。

六种架构级设计模式（Beurer-Kellner 等 14 人，IBM/ETH/Google/Microsoft），共同指导原则可直接写进设计评审：「一旦 LLM agent 摄入了不可信输入，就必须被约束到该输入不可能触发任何有后果的动作。」

6　平台层：不是「没有」，是「已出现但意味着锁定」

现象　把 agent 推上生产所需的七项能力——加密身份、执行沙箱、网络层工具治理、全链路追踪、持续评估、推理边界安全拦截、机群生命周期管理。

校正（结论方向需修改）　「没有任何一个框架提供」这一断言已被 2026 年事实推翻。Google 在 Cloud Next 2026 推出的 Gemini Enterprise Agent Platform 已同时提供 Agent Identity、Agent Sandbox、Agent Gateway、Agent Registry（Agent Identity 文档更新至 2026-09-18，凭证在网关侧加解密、agent 永远接触不到原始凭证）；Docker 亦发布 MCP Gateway 作为前置加固层。准确表述是：开源 agent 框架确实不提供这一层，但云厂商在 2026 年已补上——代价是供应商锁定与成本。把「框架没有」写成「业界没有」，结论就从「缺口」变成了「错判」，而这两种诊断导向的行动相反：前者让你去造，后者让你去选。

「1 个 agent 能自建、10 个 agent 就崩」的观察本身仍然有效。

病因　每个团队把 harness 的假设焊死进了实现。这是计算机科学的老问题——为「尚未被设想出的程序」设计系统。操作系统的答案是把硬件虚拟化成足够通用的抽象（进程、文件），抽象活得比硬件久：read() 不关心背后是 1970 年代的磁盘组还是现代 SSD。

  • session = 一切发生过的事情的 append-only 事件日志[39][39]　append-only 事件日志的实现Event sourcing（Greg Young）+ CQRS；存储用 Kafka（LinkedIn, Jay Kreps）、Postgres WAL / 逻辑解码、或 ClickHouse。现成实现：Temporal 的 workflow history、LangGraph checkpointer/store、Letta 的 message buffer。Greg Young；LinkedIn；Temporal / LangChain / Letta
  • harness = 调用模型、把工具调用路由到基础设施的那个循环
  • sandbox = 能跑代码改文件的执行环境

关键是把「大脑」和「手」解耦。手是一个极简接口 execute(name, input) → string[40][40]　沙箱即服务的 2026 供给思路即 OCI runtime spec / CRI。具体供给：E2B（Firecracker，冷启约 150ms）、Modal（gVisor，Kata 可选，能给 A100/H100）、Daytona（容器 + gVisor 层，不支持 GPU 直通）、Vercel Sandbox（2026-01-30 GA，定位「agent 的执行层」）、Cloudflare Sandbox SDK / Dynamic Workers、Kubernetes Sandbox CRD（SIG Apps 的 agent-sandbox 项目，k8s 官方博客 2026-03-20；通过 RuntimeClass 切 gVisor/Kata），以及 AWS Bedrock AgentCore Runtime（Firecracker 底座，被称作「agent 版 Kubernetes」）。E2B / Modal / Daytona / Vercel / Cloudflare / CNCF / AWS；harness 不需要知道沙箱是容器、是手机还是模拟器。容器死了，harness 当成一次工具调用错误交还给模型，模型要重试就 provision({resources}) 拉一个新的——不再需要抢救容器。harness 自身也是 cattle：session 日志在 harness 之外，崩溃后 wake(sessionId) + getSession(id) 拿回事件日志续跑[41][41]　wake / getSession / emitEvent 的商用原语Cloudflare Durable Objects 的 hibernation + alarm 是最接近的商用原语；Temporal 的 signalWithStart；底层可用 CRIU 或 Firecracker snapshot/restore 做进程级恢复。Cloudflare / Temporal / CRIU，循环中用 emitEvent(id, event) 持续写入。

收益可量化（A）：大脑移出容器后，不需要沙箱的 session 不必等容器预置，p50 TTFT 降约 60%，p95 降超 90%；扩到「多个大脑」只是起多个无状态 harness[42][42]　「无状态即可水平扩展」的出处这是 12-factor app（Adam Wiggins, Heroku）第 6 条「进程无状态」的原样复用；社区已有对应改写 「12-factor agents」（Dex Horthy, HumanLayer）。Heroku；HumanLayer。顺带解决了凭据问题（第 5 章），也解开了客户要求「连到我自己 VPC」时必须做网络对等的死结。

判据　平台团队只固化接口，不固化实现[43][43]　跨组织互通的接口层已收敛MCP（工具）、A2A v1.0（2026-01 发布，v1.0.1 加扩展机制；Linux Foundation 托管，150+ 组织，Google/Microsoft/AWS 均已集成，IBM 的 ACP 已并入）、AG-UI（前端）、AGNTCY/OASF + SLIM（Cisco，做发现与消息层）。Linux Foundation / AAIF；Cisco——对 session/harness/sandbox 的形状有主见，对背后跑什么无所谓。一个反例极具说服力：Sonnet 4.5 有「上下文焦虑」（感到接近上限就草草收尾），团队在 harness 里加了上下文重置；换到 Opus 4.5 该行为消失，那段代码变成了死重量。harness 会过期，接口不该过期。

收益与耦合　把边际成本从线性变成常数：平台层让「第 11 个 agent」的成本接近于零。但这一步只在你有第 3 个团队、第 10 个 agent 时才值得做——过早做就是过度工程。

7　上下文工程：不是独立问题，是第 2 章的物理基础

现象（B）　仅 9% 把「上下文/检索」选为最大挑战，但 47% 的 agent 失败正是「中途丢失上下文」；近 50% 在用某种 RAG。

校正　本章与第 2 章高度重叠，实质是同一现象的两种切分，列入「十大」存在重复计数。且「几乎没有标准工具支撑」过强：检索预算、上下文分层已有成熟模式，缺的是跨团队可复用的工程规范。

病因　上下文是有边际递减的有限资源，机理是三重的：transformer 让每个 token 关注所有 token，n 个 token 有 n² 对关系[44][44]　机制侧与测量侧机制侧：FlashAttention（Tri Dao）、RoPE（苏剑林）与 YaRN / 位置插值（Peng et al.）、tokenizer（BPE：tiktoken / SentencePiece）。测量侧才是可执行的：NIAH（Greg Kamradt）、RULER（NVIDIA，13 类任务，4K→128K 掉 15–64 分）、Context Rot（Chroma，测 18 个模型，无一例外退化）。Tri Dao；NVIDIA；Chroma，长度上去后捕捉这些关系的能力被摊薄；注意力模式来自训练分布，短序列远多于长序列，因此对全上下文依赖的专用参数更少；位置编码插值本身带来位置理解退化。结果是 context rot——上下文越长召回越差，呈性能梯度而非硬悬崖。

目标函数因此可以写死一句话：找到能最大化期望结果的、最小的高信号 token 集合（「最小」不等于「短」）。

机制　五种技术：

  1. Compaction[45][45]　compaction 的实现与理论原型Claude Code 的 /compact；LangGraph 的 summarization node；理论原型是 MemGPT/Letta 的虚拟内存分页（Charles Packer, UC Berkeley Sky Lab）——把 OS 的 paging 搬到上下文窗口。Anthropic / LangChain / Letta：接近上限时总结并重开窗口。调 prompt 的方法论是「先把 recall 拉满，再迭代提升 precision」。最安全的轻量形式是清理工具结果[46][46]　清理工具结果的实现与冲突实现＝在消息数组上做 span 级裁剪，保留 tool_use 但把 tool_result 替换成占位符。注意这会打破 prefix cache，与第 3 章的缓存杠杆直接冲突，需要按位置权衡。————深层历史里调用过的工具，模型没理由再看到它的原始返回。
  2. 结构化笔记 / agentic memory[47][47]　最普及的记忆系统其实是文件系统文件约定：CLAUDE.md / AGENTS.md / NOTES.md / todo 文件。产品化：Mem0（2026-04 新算法，单遍分层抽取 + 多信号检索，平均约 6,956 token/次检索，时序查询 +29.6 分、多跳 +23.1 分）、Zep/Graphiti（时序知识图）、Letta（core memory block）、Cognee。学术侧有《Everything is Context: Agentic File System Abstraction》（arXiv 2512.05470）把这条形式化。Mem0 / Zep / Letta / Cognee：把进度写到上下文之外（NOTES.md、待办、memory 工具），重置后读回自己的笔记继续跑数小时任务。
  3. 子 agent 架构：主 agent 持高层计划，子 agent 在干净窗口深挖，只回传蒸馏结果。
  4. Just-in-time 检索[48][48]　JIT 检索用的就是 Unix 工具链ripgrep（Andrew Gallant）、fd、glob、git grep、tree-sitter（Max Brunsfeld, GitHub）做结构化切分、LSP（Microsoft）做符号级跳转。混合检索：BM25（Robertson）+ embedding + reranker（Cohere Rerank / bge-reranker）；向量库 Chroma / pgvector / Turbopuffer / LanceDB。Claude Code 刻意绕开陈旧索引用 glob/grep，是对「索引一致性成本」的取舍。GitHub / Microsoft / Cohere / Chroma：不预处理全部数据，只保留轻量标识符（文件路径、存好的查询、链接），运行时按需加载。关键洞察：元数据本身就是行为信号——tests/test_utils.py 与 src/core_logic/test_utils.py 含义不同；文件大小暗示复杂度、命名暗示用途、时间戳代理相关性。这让 agent 能做渐进披露，一层层拼出理解。实践中多用混合策略（CLAUDE.md 直接进上下文，glob/grep 按需取文件，绕开陈旧索引）。
  5. Agent Skills 是渐进披露的产品化[49][49]　渐进披露的同构物Agent Skills（Anthropic，2025-12-18 开放标准，三级披露 metadata→SKILL.md→附件，可带可执行脚本）；同构物：llms.txt（Jeremy Howard, Answer.AI）、OpenAPI 的 $ref 惰性展开、MCP resources。Anthropic；Answer.AI：上下文只放 skill metadata → 触发时才读 SKILL.md → 需要时再读附带文件；skill 还能带可执行脚本（排序这类操作用代码跑远比用 token 生成便宜）。2025-12-18 已作为开放标准发布，可跨平台移植。

2026 年的重要修正：compaction / trimming 都是不可逆决策，而你无法预知未来哪些 token 会被需要。正解是把上下文存成活在上下文窗口之外的对象[50][50]　窗口之外的对象＝日志式存储等价于 Kafka offset 重放与日志式存储：存储不可变、投影可任意重算。落地即 event-sourced session log + 一个纯函数 events → messages[]。Apache Kafka；event sourcing：用 session 日志做持久存储，getEvents() 允许按位置切片——从上次读到的地方继续、回退几个事件看清前因、或在某个动作前重读。「可恢复的存储」与「任意的上下文管理」被刻意拆成两件事，因为没人能预测下一代模型需要什么样的上下文工程。

判据 / 收益　这一层的改进是减法：Sourcegraph 基准显示 5K tokens 的精准检索胜过大规模堆叠；ACE 类上下文管理在 agent 任务上超基线 10.6%、金融任务 8.6%。同一个动作既改善第 2 章也改善第 3 章——准确率上升的同时 token 下降。在模型能力提升趋缓的 2026，这是少数还能靠工程拿到两位数增益的地方。

8　可观测性：标准已经收敛，落后的是采纳

现象（B）　生产中只有 16% 监控工具调用失败、15% 监控安全/策略违规。

校正（前提站不住）　两点。其一，「8% 排名最末」来自单选排名题，推不出「被低估」。其二，事实上 2026 年可观测性恰恰是收敛最快的一层：OpenTelemetry GenAI 语义约定（gen_ai.*）已拆成独立仓库 open-telemetry/semantic-conventions-genai，覆盖 model spans、agent spans、metrics、events、exceptions 五类信号，并含 MCP 专用约定与 Anthropic / OpenAI / AWS Bedrock / Azure AI Inference 厂商约定；Google Cloud、AWS、Azure、Datadog 已采纳，Langfuse / LangSmith / Phoenix / Braintrust 全线兼容。所以这不是「缺失」，而是已有标准但采纳率滞后——对应的行动建议完全相反：不是「去造」，而是「去接」。「16% 监控工具调用失败」这个数字本身很有价值，应作为本章主证据。

病因　沿用了「请求日志」的心智模型[51][51]　对症的是「宽事件」observability 2.0 / wide events（Charity Majors, Honeycomb）——每 span 挂上百个高基数属性，查询时再聚合，而不是预先定义 metric。Honeycomb。

机制　四条理论：

  1. agent 的最小可观测单元是 trace[52][52]　span 树与 2026 的现实一次 session = 一棵 trace，LLM 调用 / 工具调用 / 子 agent 各为 span。注意 2026 的现实：GenAI semconv 已独立成 semantic-conventions-genai，但全部属性仍是 Development、无 stable release、无公开稳定化时间表 → 现实做法是采集用 OTel SDK/OTLP，语义层用 OpenInference（Arize）或 OpenLLMetry（Traceloop）并接受迁移成本。OpenTelemetry；Arize / Traceloop（一次完整会话的全部 prompt、工具调用、中间结果），不是一条请求记录。而 trace 恰好也是评估的输入——可观测性和评估是同一份数据的两种读法[53][53]　这是平台选型的判据Langfuse（开源、observability-first、OTLP 摄入，现在 ClickHouse 体系内）、Braintrust（eval-first，围绕 Eval() 实验回路与回归对比）、Arize Phoenix/AX、W&B Weave、LangSmith、MLflow Tracing（Databricks）、Opik。基础设施侧：ClickHouse（高基数列存）、Grafana Tempo、Jaeger。Langfuse / Braintrust / Arize / Databricks，不是两个系统。这解释了为什么「评估缺位」和「可观测性缺位」总是同时出现：没有 trace，误差分析根本无从做起。
  2. 不要自造 schema。自研的代价是永远无法接上生态的评估与追踪工具。
  3. 事后日志对注入类故障天然失效（见第 5 章：日志上只剩一次成功的授权调用）。因此可观测性必须包含返回值进入上下文之前的在线检查[54][54]　在线检查的工程约束分类器见 [33]；工程约束是把它放进 p99 延迟预算，通常 <50ms 且与主模型调用并发。——，即使它增加延迟且不完美。
  4. 隔离会吃掉可见性——这是必须提前预算的对话[55][55]　EDR 盲区的现状host 侧 eBPF 探测（Falco、Tetragon / Isovalent）在 VM 外只看得到一个不透明 hypervisor 进程；当前缓解是 pull-based OTLP 导出给管理员取事件日志——这是事后取证，不是实时检测，要提前和安全团队讲清楚。Falco / Isovalent。企业安全团队会问「我们的 EDR 为什么看不进去」：把 agent 关住的那层隔离同样把基于主机的检测挡在外面，从 EDR 视角，沙箱只是一个不透明的 hypervisor 进程。当前缓解是 pull-based OTLP 导出让管理员事后取事件日志，但这不等于实时监控。

最小指标清单[56][56]　最小指标清单的标准项与自定义项gen_ai.client.token.usage、gen_ai.client.operation.duration 为标准项；工具失败率、compaction 次数、策略拦截率、cost-per-resolved-task 目前都需自定义属性；「置信区间下界告警」用 bootstrap + Grafana / Prometheus alert rule。OpenTelemetry / Grafana / Prometheus：工具调用失败率与失败类型、每任务步数/token/耗时、上下文重置与 compaction 次数、策略拦截与越权尝试率、每解决任务成本、生产评分的置信区间下界。

收益与耦合　它本身产生的直接价值最少，但它是前七项收益的度量衣：多步故障定位从天级到分钟级；成本归因到具体链路（第 3 章才有靶点）；为 evals 提供真实生产样本（第 1 章才不会是离线自嗨）。没有它，你无法证明 37% 变成了更高的数字。

9　多模型与选型张力：高权限 × 低可靠性要求

现象（B）　81% 同时跑多个模型（44% 按任务路由），54% 在用开源权重模型但其中 >90% 仍同时依赖闭源模型。选型前三考量是准确度 67%、agentic 能力 53%、成本 53%——而可靠性/可用性只有 20% 进前三。提示词管理是全栈最常自建、最少采购的一层。

校正（原排序低估了它）　「可靠性仅 20%」是全篇最尖锐的发现，它不该埋在第 9 位：它与第 4 章（90% 已有写权限）直接相乘——正在给系统发写权限的同时，选型几乎不看可用性。建议把这两条合并上提为「高权限 × 低可靠性要求」。另需补一个被普遍漏掉的反向信号：超过 50% 的受访者表示正在向更少的 AI 工具收敛——「碎片化」与「标准化」是同时发生的。

病因　把模型当成不可替换的黑箱来选，而不是当成可替换零件来接。

机制　四条理论：

  1. 模型是可替换零件[57][57]　「可替换」的事实标准与抽象层事实标准是 OpenAI-compatible HTTP API（不论谁实现）。抽象层：LiteLLM（BerriAI，自托管首选，区域感知预检与成本追踪）、OpenRouter（400+ 模型零配置，5.5% 抽成，反平方路由 + fallback 链）、Portkey（Apache-2.0，语义缓存 + guardrails）、Cloudflare AI Gateway（330 数据中心，缓存/DLP/实时护栏）、Vercel AI Gateway、Helicone；SDK 侧 Vercel AI SDK、LangChain init_chat_model。BerriAI / OpenRouter / Portkey / Cloudflare / Vercel，evals 是可移植性层[58][58]　可移植性层的具体工具promptfoo 的多模型矩阵是这条最直接的工具；Braintrust / Langfuse 的 dataset + 跨模型 experiment diff；Inspect AI 用同一 task 换 solver。promptfoo / Braintrust / Langfuse / UK AISI。 能在多模型间安全路由的前提是一套与模型解耦的回归套件；否则「按任务路由」只是把不可观测的失败分散到更多供应商。第 1 章的双回路在此直接复用：换模型 = 跑一次回归套件 + 观察生产置信区间下界。
  2. 路由维度应是「任务 × 难度 × 风险」，不是价格。[59][59]　路由与语义缓存的现成实现RouteLLM（LMSYS / UC Berkeley）、Not Diamond、Martian；语义缓存 GPTCache（Zilliz），Portkey / Requesty 报 40–60% 命中率。LMSYS / Zilliz / Portkey 两个被反复验证的分层：能力分层——lead 用强模型 + subagent 用较弱模型的组合，在内部研究评估上比单 agent 强模型高 90.2%；而「升级模型」的收益大于「把 token 预算翻倍」，所以先选对模型，再谈省钱。信任分层（CaMeL）——写计划与代码的 P-LLM 必须强，只做数据解析的 Q-LLM 可以小得多，而且可以跑在用户本地，于是 P-LLM 的提供方永远看不到工具返回中的敏感数据。这是一个同时改善成本、隐私、安全的分层，不是三选一。
  3. 把可靠性写进 SLO，而不是选型打分表。[60][60]　可靠性的既有工程学Google SRE 手册的 error budget；超时 / 重试 / 熔断（tenacity、Polly、Envoy retry budget）；多供应商 failover 靠 game day 演练与混沌工程（Netflix Chaos Monkey 血统）。Google SRE；Netflix 对有写权限的系统，事故的 MTTR 不是模型质量问题，而是超时、降级、多供应商 failover 有没有演练过的问题。
  4. prompt 管理的自建不必然是浪费，但对象搞错了。 值得沉淀的是 prompt + eval + trace 三元组的版本化关联[61][61]　两条路线：平台侧关联 vs 编译路线①平台侧把 prompt 版本与 trace/score 关联——Langfuse prompt management、Braintrust、PromptLayer、Humanloop；②编译路线：DSPy（Omar Khattab, Stanford→Databricks）把 prompt 变成可编译产物，优化器 BootstrapFewShot / MIPROv2 / COPRO / GEPA（ICLR 2026，反射式自然语言优化 + Pareto 前沿选择，比 GRPO 高最多 20%、少 35× rollouts；独立仓库 gepa-ai/gepa，已有 Decagon 等生产用例）。DSPy 路线的隐含主张是：prompt 不该手写，应由 eval 反向生成。Stanford / Databricks；gepa-ai（这次改动对应哪些 trace、哪些评分变化），而不是再造一个 prompt 编辑 UI。前者没有现成商品能替你做，因为它绑定你的失败分类法；后者满地都是。

一个必须提防的新向量：多 agent 信任升级[62][62]　工程解法：类型系统里的污点标记用 UntrustedStr 之类的 newtype / Pydantic 包装类型强制边界，让「未净化内容直接进特权路径」变成编译期或校验期错误；CaMeL 的 capability 标签是同一思想的运行时版。Pydantic；Google DeepMind（CaMeL）。子 agent 可以隔离不可信内容、向上只回结构化事实；但如果子 agent 的输出因为「是自己人」而被当作比原始工具返回更高的信任级别，就引入了一条新的注入路径。分层信任与信任升级之间存在真实权衡。

判据 / 收益　供应商可替换 = 议价权与容灾，把可靠性从祈祷变成架构属性；路由本身即降本。这一层往往一次投入、三处收钱。

10　人与组织：AI 是放大器，而自评不可信

现象（C）　97% 感受到正向影响（更多实验 45%、交付更快 31%），但 93% 同时感受到负面影响：深度技术能力退化 29%、代码评审负担上升 28%、代码脆弱易出事故 22%；59% 认同「AI 生成的代码将带来重大技术负债/责任风险」；44% 表示产品组织的角色边界已显著模糊。

校正　以上全部是 C 级证据：主观感受题，不是效果测量。「深度技术能力退化 29%」是自我报告的担忧，与实际能力衰减不是一回事；「59% 认同技术负债风险」是态度分布，不是缺陷率。本章适合作为组织信号，不适合作为工程结论。

病因（最重要的一条理论）　AI 是放大器。[63][63]　放大器命题在 2026 年的机制化DORA 2026《ROI of AI-assisted Software Development》进一步给出了机制：J 曲线（价值兑现前必然先经历生产率下滑）与 verification tax（核验 AI 代码是否可靠 / 安全 / 合架构的额外成本）。结论指向同一处——回报来自内部平台质量、工作流清晰度与团队对齐，不来自工具。DORA / Google Cloud DORA《State of AI-assisted Software Development 2025》的核心论断是：AI 的首要作用是放大组织既有的优势与劣势；最大回报不来自工具本身，而来自对底层组织系统的战略投入。推论很硬——技能退化与评审过载不是 AI 的副作用，是你原本就存在的评审瓶颈、大批量交付习惯、文档缺失、内部数据不可达被放大后显形。加大 AI 投入而不修系统，只会把问题放得更大。DORA 能力目录里最直接对症的两项是「AI 可访问的内部数据」（把通用助手变成领域专家）与「清晰且已传达的 AI 立场」（模糊本身制造风险，明确政策提供实验所需的心理安全）。

机制

  • 把审查左移到确定性门禁。[64][64]　两层评审不可互相替代确定性 SAST 层 Semgrep（r2c）、CodeQL（GitHub/Semmle, Oege de Moor）、SonarQube、Snyk 负责可审计标准与漏洞；AI 评审层 CodeRabbit、Greptile、Cursor BugBot、Qodo、Graphite Agent 负责逻辑与约定。本地门禁 pre-commit（Anthony Sottile）+ ruff / mypy / eslint。Semgrep / GitHub / Sonar / Snyk；CodeRabbit / Greptile 评审负担上升的根因是人在做机器该做的检查。第 1 章的代码型 grader（测试、lint、类型、静态安全分析、fail-to-pass/pass-to-pass）应吃掉正确性与规范层；人类评审集中到意图、架构、跨系统影响——这恰是 AI 最弱、人类最不可替代的部分。从「AI 写—人审」改成「AI 写—机器判—人裁」，评审人力才不随产出线性增长。
  • 小批量纪律对人机协作同样成立。[65][65]　小批量在人类侧的同构物主干开发（trunk-based, Paul Hammant）、stacked diffs（Graphite；Meta Phabricator/Sapling 血统）——把大改动拆成按序合并的小依赖 PR，正是「一次一个 feature + 每步 commit」在人类侧的同构；配套 feature flags（OpenFeature/CNCF、LaunchDarkly）、Conventional Commits、CODEOWNERS。Graphite / Meta；OpenFeature / LaunchDarkly 第 2 章给 agent 定的「一次一个 feature + 每步 commit + 测试验证」不只是 harness 设计，同时是 PR 大小的处方。大批量 AI 生成 + 事后人肉评审，是把那 59% 的担忧变成现实的最快路径。

最反直觉的证据：不要用自评衡量收益。 METR 随机对照试验（16 位资深开源开发者，246 个真实 issue，平均 2 小时/任务，屏幕录制）：允许使用 AI 时完成任务慢了 19%；而他们事前预期加速 24%，亲身经历减速之后仍认为自己快了 20%。研究者排除了多种实验假象（用的是当时的前沿模型、遵守分组、无差异性弃题、PR 质量相当）。

必须同时说明两条边界，否则会误用这个结论：(a) METR 明确列出该研究不能证明的主张，包括「AI 不能加速大多数开发者」——他们不声称样本代表主流开发工作；(b) METR 已于 2026-02-24 宣布，由于 2025 年 agentic 工具的普及，这套任务级实验设计本身已无法给出可靠信号，第二轮 57 人的数据被判定不可靠，正在改设计。

判据　既然自评不可信、任务级 RCT 在当前普及度下又失效，衡量必须上移到交付结果[66][66]　替代计量框架DORA 四指标（变更前置时间 / 部署频率 / 变更失败率 / 恢复时间）+ cost per resolved task + 事故中 AI 生成代码占比；框架层可用 SPACE（Forsgren / Storey / Nagappan）与 DX Core 4（Abi Noda）。DORA；METR；DX：变更前置时间、部署频率、变更失败率、恢复时间，加上「每解决任务成本」与事故中 AI 生成代码的占比。不要用「团队觉得快了多少」做决策依据。

收益与耦合　DORA 的结论可直接借用：稳定性胜过速度。不修这一条，前九条省下的钱会以技术债与事故的形式在 12–24 个月后还回来。

11.1　三条必须带走的修正

  1. 成本：价格在跌（$18.40/M → $6.07/M，-67%），消耗在涨（agent ≈ 4×，multi-agent ≈ 15×）。该做路由/缓存/上下文预算/重试上限，不是去谈合同。
  2. 平台层：云厂商在 2026 年已补齐七项能力，代价是锁定。诊断从「缺口」改成「选型」，行动从「去造」改成「去选」。
  3. 可观测性：OTel GenAI semconv 已是事实标准，问题是采纳率而非存在性。行动是「去接」，不是「去造」。

以及一条必须换证据的：MCP 安全——旗舰漏洞 CVE-2025-6514 属于 2025 年 7 月，43.7 万是下载量而非受影响环境；应改用 492/2,614 零认证（19%）、92% 未用规范 OAuth、23% 有 agent 身份策略、14.4% 带完整安全批准进入生产。

11.2　结论

本文开篇引用的那句判断——「瓶颈不在模型，而在模型外面那一圈」——经过十章核查后依然成立。但需要把它的语气调低一档：2026 年真正的形态不是「什么都没有」，而是「标准和平台都已出现，采纳严重滞后，且采纳意味着锁定」。

而那一圈的图纸，其实是操作系统、能力安全（capability security）和数据流分析这些几十年的老学科——AI 工程正在做的，是把它们重新发现一遍。[75][75]　这句话的对照验证四原语的具体承载物分别是 event sourcing / 扎根理论 / Landlock-Firecracker-gVisor / Denning 信息流格。而 2026 年新增的唯一真正新东西，是 Code Mode 这一「把工具调用编译成沙箱内代码」的范式，它同时压成本、提准确率、收窄攻击面——这是全栈唯一一处三者同向的改动。综合（Cloudflare / Anthropic / Denning / AWS / Google）

十个问题最终收束为一句话：把不可测变可测，把不可控变有界。 前者解锁价值兑现（让 80% 的生产力感知变成高于 37% 的 EBIT 归因），后者保住已兑现的价值不被事故与技术债吞回去。
