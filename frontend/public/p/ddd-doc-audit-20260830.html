二「为什么」这一层:超出预期

DDD 的文档标准里最难达到的不是「写了没有」,是决策的依据留没留下。 这一项这个项目做得很硬:

docstring 里含有模块数说明
实测数字(「实测」「量出来」「N 条/篇/份」)21 / 35不是「我觉得」,是「我量过」
具体日期18 / 35能追到哪天为什么改
任务号 #NNN9 / 35能追回原始裁定
被推翻的做法(「推翻」「回退」「误报」「翻过车」)4 / 35记失败,不只记成功
一个例子说明这一项为什么值钱。
contexts/README.md 里关于 investigation 该不该有领域层,把两次相反的判断都留着: 2026-08-29 判「欠账不是事实」,于是写了 domain/carriers.py; 2026-08-30 删掉它,因为写完一直零调用。并且写明差别不在清单变了, 在中间隔着一次实测 —— 那天量下来新增的规则没有一条帮到挖材料。

大多数项目的文档只留最后那个结论。留下被推翻的那一版,下次才不会再犯同一个错。

文档写的时候是对的,后来代码变了。逐条核出来的:

「gate 凭 quotable 决定拦不拦」gate.py #155 已删

README.md整篇描述「三层级 AI 组织」roles/ 与 ai_org/ 已删;PR #7 正在重写
反过来说一句公道话:文档里那些可验证的硬约束,现在全都还成立。
contexts/README.md 声称「已用 grep 验过两条:领域层无反向依赖、领域层无 I/O」。 今天重跑:反向依赖 0 处、领域层 I/O 0 处,两条都仍然为真。

所以过时的是清单类陈述(有哪几个上下文、有哪几道门槛), 不是原则类陈述。这也说明写文档时该把可验证的约束和会变的清单分开写。

五问题二:两样一直缺的东西

甲 · ADR 被引用 12 次,但一个 ADR 文件都不存在。
ADR-1 出现 9 次(在 hotlist.py、heat.py、zhihu.py、 adapter.py、domain/README.md、contexts/README.md 里), ADR-4 出现 3 次。全仓 0 个 ADR 文件。

两条决策的内容其实都在正文里说清楚了(ADR-1:阈值是适配器的属性,不是全局常量; ADR-4:传输交给 Claude in Chrome,归一化留在代码里), 所以这不是知识丢失 —— 是引用指向空处。新人按图索骥会扑空, 而且没人知道 ADR-2 和 ADR-3 是什么、存不存在过。
乙 · 聚合的不变量从来没写出来过。
「不变量」这个词在全部 .py 和 .md 里出现 0 次 (只在一张审计 HTML 里出现过一次)。

DDD 里聚合存在的理由就是**保护不变量** —— 划这条边界是为了让某些条件永远为真。 Dossier 的 docstring 说清了边界在哪(「目录即聚合边界」), 但没说这条边界保证了什么。比如:一条 Fact 的 grade 必须是枚举里认识的词、 带 verbatim 的事实必须能追到 raw/ 里的某个原件 —— 这些是不是不变量? 现在没有一处回答。

缺了它,聚合边界就只是一个目录约定,而不是一条被强制的规则。

六要不要补

过时那 8 处该改,成本很低,而且不改会主动误导人 —— 新人读 contexts/README.md 会去找一个已经不存在的 quality 上下文。

ADR 那 12 个悬空引用,两个办法:补两份短 ADR 文件,或者把引用改成正文里的锚点。 我倾向后者 —— 内容本来就在正文里,补文件只是为了让引用有落点, 而这个项目最近三版都在做减法。

不变量那一条,值得补,而且只需要几行:在 Dossier 的 docstring 里 写清这个聚合保证什么。这是补一句真正的领域知识,不是加规则。
