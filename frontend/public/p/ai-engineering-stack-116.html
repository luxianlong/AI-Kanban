从“试一试”到“可验证”：AI Engineering Stack 十大问题的纵深解剖

摘要　本文以 2025–2026 年的一手工程材料为依据，对 AI 应用工程栈（算力→模型→推理服务→数据与检索→编排→评测→可观测→安全→应用）中的十个核心问题逐一做纵深剖析。全文采用“深度优先”结构：每个问题独立成章，沿「现象—根因—收益—求解理论—落地清单—度量信号—耦合关系」七段式贯通到底，读者可按章独立取用，亦可顺序通读以建立整栈心智模型。本文的中心论点是：该栈的瓶颈从来不是模型能力，而是验证闭环的缺失；并在结论中给出一处对通行直觉的修正——安全不是后置治理，而是拓扑约束，必须与评测、可观测同批进入架构决策。

0　导论：把 AI 系统当控制系统，而不是确定性程序

传统软件的正确性是可证明的：同一输入产生同一输出，测试通过即行为被钉死。LLM 系统的正确性只能是可测量的[4]：同一输入对应的是一个输出分布。这一性质转变具有方法论后果——工程范式必须从“验证—发布”切换为控制论的四要素闭环[6]。

控制论要素在 AI 栈中的对应物缺位后果对应问题
可观测（状态可测）trace + 完整决定性输入快照[1][5]无法归因6
可度量（误差信号）评测集 + judge + 基线[2]无法证伪1
可控（有效旋钮）上下文预算、检索、路由、权限只能玄学调 prompt2、3、5、9
有反馈（误差驱动调节）CI 门禁、灰度、回滚[3]改动无方向4、7、8、10

据此可将十个问题分为两类收益结构。问题 1、2、6 产生能力型收益：它们创造迭代信号，收益随时间复利，决定系统的天花板。其余七项多产生止损型收益：消除已经在发生的损耗，决定团队能否活到天花板。两者不可互相替代，也不宜按同一套 ROI 排序——尾部风险项（4 的不可逆操作、9 的数据外泄）期望损失极大，必须在规模化之前先行封堵。

每章统一使用以下模板，便于横向比对：现象 → 根因 → 为何要解 → 求解理论 → 落地清单 → 度量信号 → 耦合关系。

第 1 章　评测体系缺失：把玄学变成工程

1.1 现象

多数团队判断质量的方式是“人肉试几条 prompt”。没有稳定评测集，没有回归基线，因此任何改动都无法证伪：改完之后不知道是变好还是变坏，只知道“感觉不一样了”。优化退化为随机游走，团队投入与产出彻底脱钩。

1.2 根因

通行归因是“缺工具”，这是错的。真正缺的是构念（construct）：团队说不清“什么算好”，因而根本造不出误差信号。测量学上有三道关必须依次通过：

  • 构念效度：指标是否真的度量了你在乎的东西。“BLEU 高”与“客服答得好”之间没有桥。
  • 信度：judge 与人类标注是否稳定一致。
  • 统计功效：样本量决定你能分辨的最小效应。一个失败模式配 20 条以下用例，二项分布的置信区间宽到分辨不出 10 个百分点的变化[11]。

LLM 输出无标准答案、golden set 构建成本高且依赖领域专家，是这三关难过的客观原因，但不是不做的理由。

1.3 为何要解

核心收益是获得可证伪的迭代信号——这是整栈唯一能让改动收敛而非随机游走的机制。

连锁效应极强：评测集一旦存在，问题 8（模型漂移）自动获得体检工具；问题 7（换框架）获得安全网；问题 10（跨职能对齐）获得共同语言——三方吵“什么算好”变成看同一张分数表。

不解决的代价是双重的：每次优化的期望收益约等于零；更糟的是无法察觉退化，线上质量单向衰减而无人报警。

1.4 求解理论：三层成本阶梯

Hamel Husain 的三层框架仍是当前最经得起使用的组织方式，其本质是按「成本—噪声—频率」对评测手段分层：

  • L1 断言／单元测试[7]：纯确定性检查。JSON schema 是否合法[8][9]、UUID 是否泄漏、函数调用返回条数是否符合预期、禁用词是否出现。便宜、零噪声，每次代码变更都跑[17]。Rechat 这类生产系统积累到数百条断言。
  • L2 人工 + 模型评估（LLM-as-judge）[15]：处理断言表达不了的质量维度。定期跑（每日或每次合并到主干）。
  • L3 A/B 测试[18]：只在重大产品变更后跑，度量真实用户行为。

1.5 落地清单：四个多数团队做错的细节

  1. 先做错误分析，再决定样本量。 不要一上来争论“20 条还是 200 条”。正确顺序是：读 50–100 条真实 trace → 开放编码出失败模式 → 归并成失败模式分类法[10] → 为每个高频模式各配足够用例。样本量是分析的产物，不是前提。
  2. judge 对齐不要用 agreement。 Hamel 本人更新了这一点：类别不平衡时“一致率”具有极强误导性（全判通过也能拿高一致率），应分别测 judge 的 precision 和 recall[12]。
  3. judge 输出二元标签 + critique，不要 1–5 分。[13] 分级评分的标注一致性极难维持；而 critique 文本还能反过来作为高质量合成数据的筛选器，一举两得。
  4. judge 用比生产更强的模型——批判比生成更需要推理能力。并且要意识到 judge 本身是一个需要独立小评测集维护的元问题。
  5. 让看数据的摩擦为零。 自建领域化 trace 查看器（Gradio/Streamlit 一天可成）[14]，把 trace log、检索到的文档、业务系统记录聚合到一屏。工具的丑陋可以容忍，多点几次鼠标才能看到全貌不可容忍。

工程约束：评测集、rubric、judge prompt 全部进 Git[16]；L1 进 CI 门禁。

1.6 度量信号

改动到“知道好坏”的周期（从数天降到数分钟）；回归缺陷拦截率；judge 的 precision/recall 相对人工标注的漂移量。

1.7 耦合关系

问题 1 是问题 8 的前置依赖（无评测则升级红利无法兑现），是问题 7 和 10 的安全网，其燃料由问题 6 提供。

第 2 章　检索质量：被严重低估的事实上限

2.1 现象

RAG 的失败绝大多数发生在检索而非生成：分块策略粗暴、embedding 与业务语义不匹配、只做向量召回而不做混合检索与重排。表现被记录为“模型幻觉”，实际是“根本没给对文档”。

2.2 根因

这是信息论上界问题。生成端无法创造上下文里不存在的事实，因此 recall@k 是整个 RAG 系统性能的硬天花板。把幻觉归因给模型，是把测量误差记到了错误的层上。

由此得到第一条铁律：检索和生成必须分开度量[28]——recall@k / 检索命中率 归检索，faithfulness / 答案正确率 归生成。混在一起度量，等于放弃归因。

2.3 为何要解

核心收益是正确归因：把“幻觉”重新定义为“recall@k 不足”，问题性质从不可控（模型行为）转为可控（工程参数）。

杠杆倍数最高：检索是上限约束，混合检索 + rerank 通常是全栈中投入产出比最高的单项改造。

连锁效应：召回精度提升直接压缩上下文体积，同时缓解问题 3（上下文预算）与问题 5（token 成本）。

2.4 求解理论

(a) 混合检索的原理是误差不相关。 稠密向量捕捉语义[20][21][22]，稀疏 BM25 捕捉精确串[19]。用户查 “Error code TS-999”，embedding 倾向召回“一般性错误码文档”，只有 BM25 能锁定那个字面串。两者失败模式正交，因此 rank fusion 有真实增益[23][24]，而非简单叠加。

(b) 分块破坏语境，对策是 Contextual Retrieval。[26] 入库前用小模型为每个 chunk 生成 50–100 token 的“它在全文中的位置说明”，前置后再建 embedding 与 BM25 索引[29]。Anthropic 的实测数字值得作为基线记忆（top-20 检索失败率）：

方案失败率相对下降
基线（纯 embedding）5.7%—
+ Contextual Embeddings3.7%35%
+ Contextual BM252.9%49%
+ Rerank1.9%67%

配合 prompt caching（整篇文档只入缓存一次），上下文生成成本约 $1.02 / 百万文档 token——这是一次性预处理开销，相对收益极为划算。

(c) rerank 是 cross-encoder 精排[25]：粗排取约 150 条 → rerank → 送 top-20。Anthropic 实测 top-20 优于 top-10 与 top-5，但这不是普适定律——更多 chunk 同样稀释注意力，必须在自己的评测集上扫参。

(d) 2026 年的范式转移：先问“要不要 RAG”。 在投入重型流水线前先做形态判断：

  • 知识库 < 200K token（约 500 页）：直接全塞上下文 + prompt caching，不要建 RAG。索引、chunk、rerank 的全部复杂度在这里都是净损失。
  • 语料高度动态（代码库、数据库、工单系统）：走 agentic search / just-in-time 检索[27]。不预先 embed，给 agent grep/glob/SQL 等工具，让它带着轻量标识符（文件路径、查询串）按需拉取。Claude Code 即此路线，它从根本上绕开了索引陈旧问题。代价是运行时探索慢于预计算。
  • 混合策略通常最优：稳定内容（法律条款、金融产品说明）走预检索，动态部分交给 agent 自主探索[30]。

2.5 度量信号

recall@k 与端到端正确率解耦度量；单次失败的定位耗时；rerank 前后的排序位移分布。

2.6 耦合关系

检索质量直接决定问题 3 的上下文预算效率与问题 5 的成本；检索语料本身是问题 9 的攻击面（见 9.5 中的 OWASP LLM08）。

第 3 章　上下文工程与记忆管理：把窗口当预算

3.1 现象

长上下文 ≠ 会用上下文。塞满窗口带来“中间遗失”、注意力稀释与成本暴涨；多轮 Agent 的记忆压缩与摘要策略至今没有工业标准。

3.2 根因

注意力是稀缺预算，不是容量。 Transformer 的 n 个 token 产生 n² 对关系，上下文越长这些关系被摊得越薄；加之训练分布中短序列远多于长序列，模型对跨全窗依赖的专用参数更少。结果是 context rot[31]：token 数增加，召回精度下降。

关键性质：这是性能梯度而非悬崖。系统不会突然崩溃，而是持续劣化——因此它比硬错误更难被发现，也更容易被误归因为“模型不行”。

3.3 为何要解

质量与成本同向改善，这是全栈少见的非权衡项：剔除噪声段落既减轻中间遗失，又直接降低单次调用成本[40]。

额外收益：准入与淘汰规则显式化后，上下文构造过程变得可复现、可 diff、可回归测试[39]——它从“运行时偶然结果”变成“受版本控制的工件”。

不解决的代价：长会话质量随轮次单调衰减，成本随轮次线性上升——用户越活跃，体验越差且越亏钱，这是最坏的一种单位经济结构。

3.4 求解理论

目标函数：找到能最大化目标达成概率的、最小的高信号 token 集合[38]。注意“最小”不等于“短”——信息不足同样是失败模式，两侧都要防。

四个正交机制及其适用边界：

机制做什么适用场景
Compaction（压缩）[32]摘要历史后开新窗口，保留架构决策、未解 bug、实现细节，丢弃冗余工具输出需要大量来回对话的长任务
结构化笔记 / memory[34][35]写 NOTES.md、todo 到窗口外，按需拉回有清晰里程碑的迭代开发
子代理架构[36]子代理烧数万 token 探索，只回传 1000–2000 token 的蒸馏结论复杂研究、并行探索
Context editing（清除）[33]直接清掉旧工具结果或 thinking 块工具结果冗长的长循环

3.5 落地清单

  • Compaction prompt 的调法有顺序：先最大化 recall（不漏信息），再迭代提 precision（删冗余）。顺序反了会永久丢掉“当时看着不重要、后来才致命”的上下文。
  • 最轻量安全的一招是 tool result clearing：工具调用已经完成，原始返回值没必要留在历史里。Claude API 已将其产品化为 context_management 的 clear_tool_uses_20250919（以及 clear_thinking_20251015）；服务端 compaction 亦有 beta（默认 150K token 触发）。注意二者不是一回事：editing 是清除，compaction 是摘要，前者无损于既有结论，后者有信息损失风险。
  • 工具定义本身也是上下文。[37] 常见失败模式是工具集膨胀到决策点模糊——“如果人类工程师都说不清该用哪个工具，模型更不可能做对”。对策是 defer_loading + tool search 工具，或采用第 5 章的 code execution 路线。

3.6 度量信号

每轮的上下文 token 分布（按来源归类：system / 工具定义 / 检索文档 / 历史）；长会话的质量随轮次曲线；compaction 前后的关键信息保留率（可用小评测集验证）。

第 4 章　Agent 的复合错误率：让长链路可靠

4.1 现象

单步 95% 正确率，20 步后只剩 36%。非确定性使 Agent 在演示中惊艳、在生产中崩溃。多数系统缺乏检查点、回滚与 human-in-the-loop 的设计模式。

4.2 根因

0.95²⁰ = 36% 这个算式是对的，但它只在错误不可检测且不可恢复时成立——而这正是解法所在。

引入每步验证后，有效成功率变为 1 − (1−p)^k（k 为重试次数）[43][44]，指数从衰减方向翻转为收敛方向。因此核心工程目标不是提高单步准确率 p，而是让错误变得可检测。 这也是编码 agent 显著比通用 agent 可靠的唯一原因：编译器、类型检查、测试套件提供了来自环境的免费 ground truth[45]。

4.3 为何要解

解锁“长任务”这一产品形态：不做治理就只能交付演示品。检查点 + 中间态校验把指数衰减切成若干段短链路，实际可靠性回到可商用区间。

风险收益单独计：审批闸门把不可逆操作的尾部风险（误删、错误转账、错发邮件）从“概率事件”变成“需人工签字”[46][47]。这部分收益的形态是避免灾难，不是提升指标，因此不能按 ROI 与其他项并列排序。

4.4 求解理论：五条设计律

  1. 能用 workflow 就别用 agent。[41] 定义边界要清楚：workflow 是“LLM 和工具通过预定义代码路径编排”，agent 是“LLM 自主决定流程”。路径可枚举的场景用 prompt chaining（步间加程序化 gate）、routing、parallelization（sectioning / voting）、orchestrator-workers、evaluator-optimizer[42]。只有在无法预测需要多少步时才上 agent。
  2. 每步都要从环境拿 ground truth：测试结果、编译输出、schema 校验、数据库约束。没有可验证中间态的长链路必然崩。
  3. 对不可逆操作设审批闸门，并强制停止条件（最大迭代数、最大墙钟时间）[50]。
  4. 给模型一个它知道的预算。 task_budget（advisory，以 token 计，最低 20000）会向模型注入倒计时，使其自行配速并优雅收尾[49]；这与 max_tokens（硬截断，模型不知情，直接把输出砍在半句话）是完全不同的东西。混淆二者会制造“看起来是模型能力不足、实际是配置错误”的假失败——这类假失败极其昂贵，因为它会误导后续所有优化方向。
  5. 工具接口（ACI）值得和 UI 一样的投入。[48] Anthropic 构建 SWE-bench agent 时，花在优化工具上的时间超过优化 prompt。典型例子：把工具参数从相对路径改为强制绝对路径，一类错误直接归零——这是 poka-yoke（防呆）思想在 agent 设计中的直接应用。

4.5 趋势修正：别把拆分逻辑写死

METR 的 Time Horizon 1.1（持续更新）给出一个必须纳入架构决策的趋势[51]：模型能以 50% 可靠度完成的任务时长，过去六年每约 7 个月翻一番；只取 2024–2025 数据则更快，在 SWE-bench Verified 上不到 3 个月。当前前沿模型已逼近其任务集 16 小时的测量上限。

工程含义很实际：今天需要人工拆成 5 段的链路，一年后可能不需要拆。 因此不要把链路拆分逻辑硬编码进业务代码，要让分段粒度成为可调参数[52]。

4.6 度量信号

任务级成功率（而非步级）；平均人工介入次数；不可逆操作的零事故记录；单任务重试次数分布。

第 5 章　成本与延迟：让单位经济模型成立

5.1 现象

token 计费加自回归生成，使成本随用户行为线性发散；Agent 的循环调用让账单进一步失控。同时首 token 延迟（TTFT）与端到端延迟难以同时优化。

5.2 根因

成本不是常数，而是随机变量。 因此治理对象是分布（p50 / p95 / 尾部），不是均值[53]。

其次，计量单位必须是 cost per completed task，不是 cost per request[54]——一个更便宜但需要三轮重试的请求并不便宜。这是成本优化中最常见的自欺，也是多数“降本”项目事后被证明无效的原因。

5.3 为何要解

毛利可预测：分层路由与缓存通常带来数倍级成本下降，熔断把最坏情况账单封顶。这直接决定产品能否定价、能否规模化。

战略收益：成本下降释放预算去做质量投入（更多召回、更多校验、更强模型兜底），形成正循环。

不解决的代价：增长即亏损，运营被迫用限流损害体验来保住成本——这是产品死亡螺旋的标准起点。

5.4 求解理论：先免费杠杆，后权衡杠杆

免费杠杆（做完这些再谈别的）

  • Prompt caching。[55][57] 原理是前缀精确匹配：渲染顺序为 tools → system → messages，前缀中任何一个字节变化，其后全部失效。因此稳定内容（冻结的 system prompt、排序确定的工具列表）必须在前，易变内容（时间戳、请求 ID、本次问题）放在最后一个断点之后。
    验证方法：观察 usage.cache_read_input_tokens。若重复请求下它恒为 0，说明存在静默失效源；最常见的三个是 system prompt 里的 datetime.now()、未排序的 JSON、每次都在变的工具集[56]。
  • Batch API：非实时任务 50% 折扣[58]。
  • 输入/输出 token 卫生：第 3 章的 context editing 同时是成本杠杆。
  • 工具定义瘦身——这里有数量级机会。[59] 把 MCP 服务器暴露成代码 API 而非直接工具调用，agent 通过文件系统按需读取工具定义，并在执行环境里过滤中间结果，Anthropic 实测 150,000 → 2,000 token（−98.7%）。原理有两层：一是工具定义渐进披露，二是中间结果不再两次穿过上下文（10,000 行表格在沙箱里 filter 完只回传 5 行）。

权衡杠杆（会动质量，必须配评测）

  • Effort 档位（low/medium/high/xhigh/max）是第一个质量交易旋钮，且应按路由分别调，不要全局调[61]。编码与长程 agent 任务对高 effort 回报强烈；对话、分类、高并发路由通常 low/medium 足够。
  • 反直觉但重要：在搭建多模型级联之前，先测“最强模型 + 低 effort”。原因有二——新一代模型的低 effort 常常超过上一代的高 effort；且缓存是按模型分域的，级联会放弃跨模型缓存复用，省下的单价可能被丢失的缓存命中吃光[60]。
  • 中途修改顶层 effort 会使消息缓存失效；用 per-message 的 system message 传 effort 可避开这次重置。

延迟：TTFT 与端到端必须设两个独立 SLO，因为它们的优化手段互相冲突（缓存优化 TTFT，批处理优化吞吐）[62][63]。把条件分支下沉到代码执行环境（让 if 语句由运行时判断而非模型评估）可同时节省 TTFT 与 token。极端延迟敏感路径可用 fast mode（约 2.5× 输出速度，溢价定价；注意切换 speed 同样使缓存失效）[64]。

5.5 度量信号

cost per completed task 的 p50/p95；缓存命中率（cache_read_input_tokens 占比）；TTFT 与端到端延迟分别的 SLO 达成率；单功能 token 预算的熔断触发次数[65]。

第 6 章　可观测性断层：获得归因能力

6.1 现象

传统 APM 看不懂 prompt、trace 与工具调用链。出问题时缺少完整输入快照（含检索到的文档、模型版本、采样参数），线上问题无法复现，事故复盘变成猜测比赛。

6.2 根因

可复现性要求你能重建完整的决定性输入。一次 LLM 调用的本质是：

f(精确模型版本, 渲染后的全部输入 token, 采样/effort 配置) → 输出分布

三项中少记任何一项，线上问题就永久不可复盘[73]。传统 APM 记录的是 HTTP 状态码和耗时——恰好是最不相关的两个维度[69]。

6.3 为何要解

核心收益是线上问题可复现：事故从“不可调查”变为“可回放”。

基础设施价值更大：真实 trace 是最廉价的评测集来源——问题 6 的产出直接喂给问题 1。这是整栈最重要的一条内部管线，也是复利链条的起点。

6.4 求解理论

(a) 往标准靠，别绑死厂商 SDK。[66][67] OpenTelemetry 的 GenAI 语义约定已从主 semconv 仓库独立拆分为 open-telemetry/semantic-conventions-genai，覆盖 GenAI 客户端推理、agents、工具执行、评测以及 MCP 操作，属性命名空间为 gen_ai.* / mcp.* / 厂商特定前缀。拆分出独立仓库本身就是信号：该领域的约定演进速度已与通用 semconv 脱节。

选型原则：厂商平台可以换，语义约定不能换。[68] 把 trace 写成符合 gen_ai.* 的 span，迁移成本就从“重写埋点”降为“换 exporter”。

(b) 每个 LLM span 的必录字段（“一等日志”的具体清单）：

  • 精确 model id（不是 claude-opus，是完整版本串）
  • 渲染后的最终 system / messages / tools 定义（不是模板，是变量替换完成之后的文本）
  • output_config（effort、format）与采样参数
  • usage 全量，含 cache_read_input_tokens / cache_creation_input_tokens
  • stop_reason 与 stop_details
  • TTFT 与端到端耗时，分开记
  • 检索层：query、召回的 doc id + 分数、rerank 前后排序
  • 层级关系：session → trace → span（LLM call / retrieval / tool call）[70]

(c) 三个实操约束：

  1. 全量落盘成本高 → 头部采样 + 错误 100% 采样[71]；
  2. PII 在写入前 tokenize[72]；
  3. 把在线 judge 挂在采样的生产 trace 上[74]——这一步同时喂饱问题 1 与问题 6，是整个闭环最关键的一条回流边。

6.5 度量信号

MTTR；能复现的线上投诉占比；trace 覆盖率（有完整决定性输入的调用比例）。

6.6 耦合关系

问题 6 是问题 1 的燃料来源、问题 8 灰度回归的观测面、问题 7 的检验标准（若三层抽象让你看不到最终 prompt，你的 trace 就是残缺的）。

第 7 章　框架抽象过度与生态 churn：保住主动权

7.1 现象

编排框架版本迭代快、抽象层层包裹，调试时要穿透三层才能看到真实 prompt；向量库、网关、Agent 协议选型极易锁定或推倒重来。

7.2 根因

违反了稳定依赖原则[75]：核心业务逻辑依赖了比自己变化更快的东西。解法是依赖倒置——依赖协议，不依赖框架[76]。协议演进慢、有版本协商、有向后兼容承诺；框架抽象每个 minor 版本都在变。

7.3 现状修正：标准其实已经定了

“MCP/A2A 标准未定”这一判断在 2026 年已不准确。分工已经确定[77]，仍在演进的是扩展层：

  • MCP（agent ↔ 工具）当前规范版本 2026-07-28。架构上已演进为无状态、自包含请求 + 每请求能力协商——这对可伸缩性和可观测性都是好消息。核心之外的能力走显式 opt-in 的扩展机制，双方在初始化时协商：Tasks（长任务异步执行，含轮询、中途输入、持久句柄）、Skills over MCP、MCP Apps（对话内联 UI）。这个设计本身就是抗 churn 的答案[78]：核心稳定，实验性能力在扩展层，客户端不支持则自动降级。
  • A2A（agent ↔ agent）已由 Google 捐给 Linux Foundation，技术指导委员会包含 AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow，官方 SDK 覆盖 Python/JS/Java/C#/Go/Rust。它明确声明不是 MCP 的替代品，也不是 agent 框架：MCP 管 agent 装备工具，A2A 管 agent 之间跨框架协作。

7.4 求解理论：三条架构律

  1. 核心逻辑与框架解耦。 prompt、状态机、评测、检索配置放在自己的模块里，框架只做 adapter。Anthropic 自己的建议是直接从 API 起步[79]——很多模式只要几行代码；用框架的前提是“你能读懂底下发生了什么”，因为错误的底层假设是客户出错的常见来源[80]。
  2. 保留“能打印出最终 prompt 和最终 HTTP 请求”的能力。[81] 这既是调试能力，也是问题 6 的前置条件。
  3. 对可换组件只用最小公共接口面。[82] 向量库只用 upsert/query/filter，rerank 走独立服务，网关层统一 usage 语义。每多用一个厂商特有特性，迁移成本就上一个台阶。

7.5 收益与度量

核心收益是降低选型错误的代价：换编排框架/向量库/协议从“重写”变成“换适配层”。日常收益是调试耗时从穿透三层抽象降到看一眼日志。度量信号：替换一个组件的估算工期；从报错到看到最终 prompt 的耗时。

第 8 章　模型版本漂移：让升级从风险变为红利

8.1 现象

供应商更新或弃用模型，同一 prompt 行为改变；自研微调模型存在训练/推理不一致。精心调优的 prompt 是对特定模型版本的过拟合。

8.2 根因与 2026 年的硬化

根因判断正确：prompt 是对特定模型版本的过拟合参数[90]，因此模型 ID 是一个依赖版本，必须 pin 并纳入 lockfile 管理[83]。

但 2026 年的真相比“行为漂移”更硬——它已经是 API 契约的硬断裂[84]。以 Claude API 当前状态为例：

  • temperature / top_p / top_k 在 Opus 4.7 及以后设为非默认值 → 400 错误；Python SDK 1.x 干脆移除了这些参数，传入直接 TypeError。
  • budget_tokens（固定思考预算）在新一代模型上被移除 → 400，取而代之的是 thinking: {type: "adaptive"} + output_config.effort。
  • Assistant prefill（预填最后一轮助手消息）在 4.6 及以后全家族 → 400。
  • 强制工具调用 tool_choice: {type: "any"|"tool"} 在最新一代上 → 400。

含义：升级不再是“跑回归看指标掉没掉”，而是“先过编译/契约检查，再跑回归”。好消息是硬失败比静默劣化好定位得多。

另一半好消息：生命周期现在有明确 SLA[87]，“供应商静默更新”这个假设需要更新。Anthropic 定义了 Active / Legacy / Deprecated / Retired 四态，退役前至少 60 天邮件通知，并为每个在役模型公布“不早于某日”的暂定退役日期（例如 claude-opus-5 不早于 2027-07-24，claude-sonnet-5 不早于 2027-06-30）。这把一个不可预测风险转化为可排期的工程事项。

8.3 为何要解

核心收益是能安全地享受模型进步：固定版本 + 灰度 + 全量回归后[88][89]，“上新模型”从赌博变成一次带回滚的常规发布——底层能力每次进步都能被产品实际吃到。

稳定性收益：消除“什么都没改但线上变了”这类最消耗团队信任的事件。

前置依赖：该收益完全建立在问题 1 之上，无评测集则无法兑现。

8.4 落地清单

  1. Pin 精确 model ID。 注意新一代 ID 不带日期后缀（是 claude-opus-5，凭记忆补日期反而会失败）；旧世代才带。
  2. 定期审计存量用法：Console → Usage → Export CSV，按 API key 和 model 拆分，找出仍在调用已弃用模型的角落。
  3. 运行时能力发现用 Models API（max_input_tokens / max_tokens / capabilities），不要硬编码上下文窗口常量[86]。
  4. prompt 与模型版本一起版本化，升级走灰度 + 全量评测回归。
  5. 别忘了 prompt 本身的“陈旧模式”。[91] 为上一代弱模型写的东西——冗长的分步 CoT 指令、塞满边界情况的 if-else 式 prompt、“不要过度思考”之类的规则——在新模型上往往反而降低质量。迁移时 prompt 审计与代码审计同等重要，而且它不会报错，只会让你误以为“新模型也就那样”。
  6. refusal 是 HTTP 200，不是异常。[85] 安全分类器拒答时返回 stop_reason: "refusal" 而非抛错。没有先判 stop_reason 就读 content 的代码，会在生产里静默返回空串。生产路径应配服务端 fallback。

第 9 章　安全面全新且防御不成熟：从过滤转向架构约束

9.1 现象

提示注入没有根本解法；工具权限过宽；模型输出直接进入下游执行。

9.2 根因

指令与数据同通道，这是架构缺陷而非模型缺陷。所有 token 最终被拼成一个序列喂进模型，模型在原理上无法可靠区分“来自运营者”与“来自被摘要的网页”。它与 SQL 注入同构，但没有参数化查询的等价物[95][96]——这是它至今无解的根本原因。

9.3 证据链：2025 年最重要的安全结论

《The Attacker Moves Second》（Nasr、Carlini 等 14 位作者，含 OpenAI、Anthropic、Google DeepMind）对 12 种已发表防御施加自适应攻击（梯度下降、强化学习、随机搜索、人工引导）[98]。结果：多数防御的攻击成功率 >90%，而这些防御原本报告接近 0%；500 人红队竞赛的成功率是 100%。

两条直接推论：

  1. 静态样本集评估防御几乎没有信息量，必须做自适应评估。
  2. 宣称“拦截 95% 攻击”的 guardrail 产品不能作为安全控制点[99]——Web 安全里 95% 是不及格分。它可以是纵深防御的一层，不能是那一层。

9.4 求解理论：Lethal Trifecta 与 Rule of Two

Lethal Trifecta（Simon Willison）[92]：私有数据访问 + 接触不可信内容 + 外发能力，三者齐备即可被窃数据。

Agents Rule of Two（Meta，2025-10-31）[93]把它推广到数据泄漏之外：

在稳健检测成为可能之前，agent 在一个 session 内最多满足以下三条中的两条：
[A] 处理不可信输入　[B] 访问敏感系统或私有数据　[C] 改变状态或对外通信
三条全需要时，不得自主运行，至少需要 human-in-the-loop 审批或其他可靠验证。

两点必须注意：Meta 已把交集标签从 “safe” 改为 “lower risk”；且 Simon 指出 A+C（不可信输入 + 改状态）即便没有 B 也可能造成实质危害，这个组合不应被当作安全区。

9.5 落地手段：物理性地切断某条边

切断的边手段
切 [B]最小权限工具；沙箱/隔离环境，agent 能改状态但改不到要紧的系统[101]
切 [C]出站域名白名单；禁止工具发起任意 HTTP；注意图片加载、链接渲染都是外发信道[100]
切 [A]新 session = 新上下文窗口，处理完不可信内容后重开，trifecta 被重置[97]
结构性Code execution 的 PII tokenize：模型只看到 [EMAIL_1]，真实值在执行环境里从一个系统流向另一个系统，从未进入模型上下文。这是架构级的边切断，不是过滤[102]
输出侧strict: true / structured outputs 做 schema 校验；下游执行前沙箱化
通道分离运营指令走 mid-conversation system message（{"role": "system"} 追加到 messages），而非拼进用户消息——这是目前对 prompt injection 更安全的 operator channel，且不打断缓存前缀[103]

补充覆盖度清单：对照 OWASP GenAI Security Project 的 LLM Top 10（2025 版）[94]，尤其 LLM08 向量与嵌入弱点——提醒你 RAG 语料本身也是攻击面（知识库投毒、多租户 embedding 串泄），这是“只盯着用户输入”的团队普遍的盲区[104]。

9.6 为何要解

这是唯一关乎存续而非效率的一项。切断三角中任意一条边，把数据泄露从“可被利用”降为“需绕过多层”。

商业收益：最小权限、schema 校验、沙箱执行是企业客户与合规审计的准入门槛——没有这套，很多市场根本进不去。

认知前提：提示注入无根本解法，收益来自架构性降低损害面，而非指望检测能拦住。

第 10 章　工程规范与组织断层：把个人能力变成组织能力

10.1 现象

Prompt 散落在代码字符串里无版本控制；Notebook 到生产之间缺少交付路径；数据科学、后端、产品三方对“什么算成功”定义不一致。

10.2 根因

交付物的边界被重新划定了，但流程没跟上。 在 AI 系统里，决定行为的输入不只是代码，还包括：prompt、工具 schema 与描述、评测集、judge rubric、检索配置（chunk 策略、top-k、rerank 阈值）、模型 ID 与 effort 档位。这些全都是源代码。[105] 任何一项躺在 Notebook、Notion 或某人本地，系统就不可复现。

10.3 求解理论

(a) 一切进 Git 与 CI。[106][107] 清单：prompt 模板、tool 定义、评测集、judge prompt、检索配置、模型 ID pin、SKILL.md。PR 触发 L1 断言，合并前看评测指标 diff[109]。

(b) 用“评测指标即合同”统一三方口径。[108] 三方定义冲突的根源是没有共同的数字。把验收 SLO 化：

功能 A：pass rate ≥ 92%（对该功能的 L1+L2 评测集）；p95 端到端 ≤ 3.5s；cost per completed task ≤ $0.04；不可逆操作 100% 经审批闸门。

分工随之自然对齐：产品定义 rubric，数据科学实现并校准 judge，后端保证 trace 覆盖率。[113] 三方不再争论“这算不算 bug”，而是争论“这个阈值定多少”——后者是可决策的。

(c) 一份代码跑三处。[110] 同一套 eval runner 用于本地开发、CI 门禁、生产 trace 回放。这条消除 Notebook 到生产的断崖[111]——没有“移交”，只有同一入口的不同数据源。

(d) 方法论的杂交配方。[112] 借 ML 的「数据集 / 指标 / 实验记录」，借 SE 的「版本 / CI / 灰度 / 回滚」，但节奏按 SE 走（每个 PR 都跑 L1，而不是每个 sprint 跑一次评测）。AI 工程之所以两边都不服帖，是因为多数团队各取了一半却按 ML 的节奏运行[114]。

(e) 把 agent 的脚手架也纳入版本管理。[115] 这是 2026 年新增的一层：agent 自己写出的可复用函数，加一个 SKILL.md 就成为结构化的 skill，被后续调用复用。让 agent 逐步积累能力工具箱是好事——但这些 skill 必须进 Git、进 review、进评测，否则你会得到一个行为不断漂移且无人知道原因的系统。

10.4 收益与度量

核心收益：交付路径从“某个人的 Notebook”变成流水线，改动可评审、可回滚、可追责。组织收益：把讨论从立场之争拉回指标之争。规模化收益：新人上手周期与人员流动风险显著下降，知识沉淀在仓库而非个人脑中。

度量信号：受版本控制的行为决定性配置占比；从提交到获得评测 diff 的耗时；新人首次独立提交 PR 的天数。

结论：依赖图与修正后的投入顺序

收益结构总判断

  1. 复利链条：可观测（6）产出真实 trace → 喂养评测（1）→ 使检索（2）、上下文（3）、版本升级（8）的优化可度量 → 每一轮改进都被固化（10）。这条链投一次、受益持续。
  2. 止损优先级：安全（9）与 Agent 不可逆操作（4）属于尾部风险，期望损失极大，应在规模化前先封堵，不应按 ROI 排序。
  3. 两处对通行直觉的修正：
    • 修正一：安全（9）必须前移到第一批。 Rule of Two 是拓扑约束——它决定 agent 能不能同时碰不可信内容、私有数据和外发能力。这一决定一旦体现在架构里（工具集怎么分、session 怎么切、出站怎么管），后期改动成本极高。而防御性过滤已被《The Attacker Moves Second》证明不可依赖，因此不存在“先上线再加 guardrail”这条退路。
    • 修正二：检索（2）的形态正在迁移。 在投入重型 RAG 流水线前，先判断场景是否应走“全塞 + 缓存”（<200K token）或“agentic search”（动态语料）。为已经过时的形态建一套 Contextual Retrieval + rerank 流水线，是昂贵的错误。

建议投入顺序

1. 评测（1）            ── 没有它，后面每一步都无法判断是否有效
2. 可观测（6）          ── 归因能力，同时是评测集的燃料来源
3. 安全架构边界（9）    ── 拓扑决策，越晚改越贵
4. 检索 + 上下文（2、3）── 事实基础与注意力预算，两者同源
5. 成本治理（5）        ── 先做完免费杠杆（缓存、工具瘦身、batch）
6. 版本与规范（8、10）  ── 把前五项的产出固化进 CI
7. Agent 复杂度扩展（4、7）── 最后再扩，且 METR 趋势意味着别把拆分逻辑写死

顺序不可随意颠倒的理由是：后段每一项的收益兑现都依赖前段提供的验证与归因能力；顺序颠倒会导致投入无法被证明有效，进而在组织内被砍掉——这是许多 AI 平台团队真实的死因。

最终判断

十项全解的终局不是“模型更强”，而是获得一个可信的验证闭环：团队从“试一试看看”转为“提出假设、度量、固化”。这个栈的瓶颈从来不是模型能力，而是你有没有能力知道自己做得对不对[116]。问题 1 和 6 解决“知道”，问题 9 解决“在知道之前不要把自己置于危险拓扑”，其余七项在前三项到位后，大多会降级为可调参数。

  6. 头部采样 + 错误 100% — 库OTel Collector tailsamplingprocessor / probabilisticsampler。出处：OpenTelemetry。

  8. “能重建完整决定性输入” → 可回放 — 库VCR.py / pytest-recording 录制真实 HTTP；Temporal replay test；确定性回放。出处：VCR.py 社区；Temporal。

问题 7｜框架抽象过度与生态 churn

  1. 稳定依赖原则 — 方法论SDP：依赖只能指向更稳定的方向。出处：Robert C. Martin（Uncle Bob）。
  2. 核心逻辑与框架解耦 — 方法论Ports & Adapters（六边形架构）；DDD 防腐层（ACL）包住框架。出处：Alistair Cockburn；Eric Evans。
  3. “依赖协议，不依赖框架” — 协议MCP（2026-07-28；无状态自包含请求 + 每请求能力协商；Tasks / Skills over MCP / MCP Apps 为显式 opt-in 扩展；现属 LF Projects）；A2A（Linux Foundation，Google 贡献，六语言官方 SDK，Agent Card 发现 + JSON-RPC 2.0 over HTTP(S) + SSE/push）。出处：Anthropic（MCP）；Google → Linux Foundation（A2A）；另有 AGNTCY（Cisco/LF）。
  4. 「扩展机制本身是抗 churn 的答案」 — 协议核心稳定 + 能力协商降级 —— 与 LSP 同源设计（MCP 明言受 LSP 启发）。出处：Microsoft（LSP）的设计遗产。
  5. “直接从 API 起步” — 库anthropic SDK、httpx；OpenAI-compatible /v1/chat/completions 已是事实标准（vLLM 同时原生支持 Anthropic Messages API 与 gRPC）。出处：Anthropic；vLLM 社区。
  6. 要类型与结构，但不要全家桶 — 库Pydantic AI、BAML（自带 prompt DSL + 编译期类型）、Instructor、Outlines、Vercel AI SDK + Zod。出处：Samuel Colvin；Boundary；Jason Liu；dottxt；Vercel。
  7. “能打印最终 prompt 和最终 HTTP 请求” — 语言特性/工具ANTHROPIC_LOG=debug、SDK with_raw_response、httpx event hooks、mitmproxy 代理抓包。出处：Anthropic SDK；mitmproxy。
  8. 最小公共接口面 — 库/规范pgvector（接口就是 SQL）、rerank 走独立 HTTP 服务、LiteLLM 统一 usage、OpenFeature 统一开关。出处：CNCF（OpenFeature）。

问题 8｜模型版本漂移

  1. 模型 ID 是依赖版本，要进 lockfile — 库uv.lock / poetry.lock / pnpm-lock 管代码依赖；模型 ID 放同级的受版本控制 config（Hydra / Pydantic Settings），不散落在代码里。出处：Astral（uv）；Meta（Hydra）。
  2. “先过契约检查，再跑回归” — 语言特性参数移除在 Python SDK 里是 TypeError → mypy/pyright 在 CI 即拦截；API 层 400 → 契约测试。出处：Microsoft（pyright）；Pact（contract testing，Ron Holshausen / SmartBear）。
  3. refusal 是 HTTP 200 不是异常 — 语言特性语言级解法：把 stop_reason 建模为可辨识联合 / sum type 并强制穷尽匹配——Rust match、TS discriminated union + never 兜底、Python match + assert_never。出处：Rust / TypeScript / PEP 634 + typing.assert_never。
  4. 运行时能力发现，不硬编码窗口常量 — APIAnthropic Models API（max_input_tokens / capabilities）、OpenAI /v1/models。出处：Anthropic / OpenAI。
  5. 弃用有 SLA → 可排期 — 规范工程侧对应：Deprecation 头（RFC 9745）、Sunset 头（RFC 8594）的同构治理；Console → Usage → Export CSV 审计存量。出处：IETF；Anthropic。
  6. 灰度 + 全量回归 — 基础设施Argo Rollouts / Flagger（金丝雀）、shadow traffic（双写不返回）、LaunchDarkly / Statsig 按 key 分流。出处：Intuit + CNCF；Weaveworks。
  7. 跨模型回归 — 框架promptfoo 的 provider 矩阵、Inspect 同一 eval 跑多模型、golden snapshot diff。出处：promptfoo；UK AISI。
  8. “prompt 是对旧模型的过拟合参数” → 迁移要重编译 — 框架/论文DSPy：写 Signature/Module，换模型后用 optimizer 重编译而非手改 prompt；GEPA（反思式 prompt 进化，可超过 RL）。出处：Omar Khattab, Matei Zaharia, Christopher Potts 等，Stanford NLP；GEPA（Jul'25）。
  9. 旧式 prompt 模式的识别 — 方法论审计冗长 CoT 指令、if-else 式边界堆砌（新模型上反而降质）；配 Anthropic prompt improver。出处：Anthropic。

  3. 覆盖度清单 — 规范OWASP GenAI LLM Top 10（2025），尤其 LLM08 向量与嵌入弱点；MITRE ATLAS；NIST AI RMF + AI 600-1。出处：OWASP GenAI Security Project（Steve Wilson）；MITRE；NIST。
  4. “没有参数化查询的等价物” → 从过滤转向架构 — 论文/代码CaMeL：P-LLM 生成受限 Python 代码，Q-LLM 只解析不可信数据、绝不发指令；能力标签随数据流传播，由自定义解释器强制策略。出处：Debenedetti, Shumailov, Fan, Hayes, Carlini, Fabian, Kern, Shi, Tramèr —— Google + Google DeepMind + ETH Zurich，Defeating Prompt Injections by Design。

一条贯穿全栈的选型判据

  1. 把赌注押在协议和语言特性上，把框架当 adapter — 方法论上列脚注中真正不可替换的只有三类：协议（MCP、A2A、OTel gen_ai.*、OAuth 2.1/RFC 8707、W3C Trace Context）、语言特性（类型系统、sum type 穷尽匹配、确定性序列化、determinism checker、能力/信息流模型）、方法论论文（RRF、PagedAttention、CaMeL、Rule of Two、SDP、ML Test Score）。其余全是可换的实现——框架（LangGraph/Agents SDK）、后端（Langfuse/Braintrust）、向量库（pgvector/Qdrant）、judge 平台，都应被防腐层隔在核心逻辑之外。对应关系：Inspect/promptfoo 给你“知道”，OTel GenAI semconv 给你“归因”，CaMeL/Rule of Two 给你“知道之前先别把自己放进危险拓扑”。
