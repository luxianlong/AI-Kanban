AI 工程技术栈的系统性问题研究：一种以问题为轴的纵深剖析

摘要

AI 工程技术栈（AI Engineering Stack）的核心矛盾可以概括为一句话：用概率性组件构建确定性产品。本文不按技术分层组织，而是以「问题」为纵轴，对该技术栈中的十类系统性问题逐一做深度剖析。每一个问题都沿四个维度贯通展开——问题机理（它为什么存在）、严重性评估（它有多要紧、何时要紧）、理论基础（用什么原理求解）、收益结构（解决后获得什么）。这种"深度优先"的组织方式使读者可以独立读懂任一问题的完整闭环，也可以顺序通读，获得整栈的系统认知。

本文的核心论断有三：其一，绝大多数 AI 系统故障不是"模型不够强"，而是缺少把不确定性约束住的工程设施；其二，评测与可观测性是零阶项——它们自身不创造价值，却决定其他一切投资能否被验证与兑现；其三，若干被普遍低估的问题（检索层越权、Agent 写权限、Agent 成本无上界）实际具备 Critical 等级，且其中部分属于准入问题而非优先级问题。

〇、导论：系统边界与一条主定理

0.1 分层与耦合

典型 AI 工程栈自下而上可分为六层：

层级组成代表形态
L1 算力层GPU/TPU、网络、存储云实例、自建集群
L2 模型层基座模型、微调模型、EmbeddingAPI 模型 / 开源权重
L3 服务层推理引擎、路由、缓存、限流vLLM、网关、模型路由
L4 编排层Prompt、RAG、Agent、工具调用、工作流框架 / 自研编排
L5 数据层向量库、知识库、特征、日志与回流检索 + 语料管线
L6 运维层评测、可观测、成本、安全、合规Eval、Trace、护栏

关键观察：问题几乎全部产生于层与层之间的耦合，而非单层内部。单层内部的问题（推理引擎的吞吐、向量库的召回延迟）已有成熟解法；真正难的是跨层的语义传递——检索质量如何影响生成正确性、模型版本变化如何静默地击穿业务假设、Agent 的一步误判如何外溢为真实世界的不可逆操作。

0.2 主定理：必要多样性

控制论的 Ashby 必要多样性定律（Law of Requisite Variety） 给出了唯一可行的路径：控制器的多样性必须 ≥ 被控对象的多样性。LLM 的输出空间是天文数字量级，工程上不可能靠"把模型调对"来匹配这个多样性，只能靠在外部加装约束环（constraint loop），压缩系统的有效状态空间。

由此，本文将出现的所有解法归为三类算子：

  • 压缩（Reduce）[1]：缩小输入/输出空间 → 结构化输出、schema 约束、枚举化、检索收窄
  • 测量（Measure）[2]：把不可观测量变成可观测量 → 评测、Trace、成本计量
  • 围栏（Bound）[3]：把失败后果限制在可承受范围 → 闸门、幂等、审批、回滚

每个问题的解法，本质上都是这三类算子的某种组合。

第一章 不确定性与工程确定性的根本冲突

1.1 问题机理

传统软件的正确性是逻辑命题：给定输入，输出要么符合契约，要么违反契约，P 真或假。LLM 的正确性是随机变量：同一输入在不同时间（模型版本、温度、上下文顺序、后端负载）会产生不同输出，其正确性只能用分布描述。

把布尔断言强行套在随机变量上，必然导致三种病态现象：

  1. 单元测试失效：assert(output == expected) 变成随机红绿灯，团队最终选择删除或忽略这些测试
  2. 回归基线缺失：无法判断"这次变差了"是真实退化还是采样噪声
  3. 故障不可复现：线上报告的 bug 在本地跑十次全是正常的，调试退化为猜测

1.2 严重性评估

维度评估
影响面全栈（L2–L6 全部受影响）
可逆性不适用——这是属性而非缺陷
发生概率100%
检测难度低（一开始就能感知）
综合等级High（结构性约束，非可修复缺陷）

关键判断：这是整个技术栈的公理，不是可以"修复"的问题。它的危险之处不在于自身，而在于团队误以为可以用传统工程手段消除它。

误判风险：把它当成 bug 去修（设 temperature=0、写更严格的 prompt 约束、加更多 few-shot），会消耗大量工程投入而收效有限。正确的处理是"约束"而非"消除"。

结论：等级 High，但优先级不独立——它必须通过第二章（评测）来管理。单独立项是浪费。

1.3 理论基础：统计过程控制与契约弱化

求解理论的核心是：将验收契约从「点断言」升级为「分布断言」[4]。

设质量指标 q 为随机变量，用 n 次采样估计均值与置信区间。判据从

assert(output == expected)

变为

assert(CI_lower(q) ≥ threshold)

进一步借用 Shewhart 控制图的核心区分[6]：

  • 常见原因变异（common cause）：模型固有噪声，不该报警
  • 特殊原因变异（special cause）：模型换版、prompt 改动引入的系统性偏移，必须报警

只有超出 ±3σ 控制限才触发调查。这一区分使监控从"每天都在响"变成"响了就是真事"。

三条工程推论：

  1. 任何单次对比（"我试了一下这个 prompt 更好"）在统计上无效——样本量 n=1 的噪声大于绝大多数真实效应。这是团队内部 prompt 争论无法收敛的数学原因。
  2. 固定随机源（temperature=0、seed、上下文顺序）的价值不是"让模型确定"，而是方差削减[5]，把不可控噪声降到可测量水平，从而让真实效应浮出信噪比。
  3. 契约边界应设在可验证的结构层：输出 schema、类型、取值域、引用 ID 是否存在——这些可以做硬断言；语义正确性只能做分布断言。因此工程设计的方向是尽可能把语义判断转化为结构判断[7]（让模型输出枚举值而非自由文本，输出引用编号而非复述原文）。

1.4 收益结构

解决方式的本质不是消除不确定性，而是把它约束在可测量的区间内。收益体现为：

  • 可回归：变更有基线，测试从「通过/失败」升级为「分数分布是否退化」，回归测试重新生效
  • 可复现：固化随机源与上下文顺序后，故障可复现，调试时间从"天"降到"小时"
  • 可承诺：对外可给出「95% 场景正确率 ≥ X」的 SLA，而非模糊承诺

量化指标：缺陷复现率、变更后回归发现率、平均故障定位时间（MTTI）

不解决的代价：每次发布都是赌博，线上问题只能靠用户投诉暴露。

第二章 评测缺失

2.1 问题机理

绝大多数团队在没有评测集的情况下上线。表现为四种典型症状：

  1. 用「感觉变好了」替代指标，迭代变成随机游走
  2. LLM-as-judge 自身有偏差，且随评判模型版本漂移，测量仪器本身在移动
  3. 线上效果与离线指标脱节，缺少真实分布的评测数据
  4. 评测成本高 → 评测频次低 → 反过来放大漂移

2.2 严重性评估

维度评估
影响面全栈，且是所有改进的验证通道
可逆性高（随时可补建，但成本随时间指数上升）
发生概率约 80% 的团队处于缺失或形式化状态
检测难度极高——缺失评测的团队恰恰无法发现自己在退化
综合等级Critical（P0，根因级）

这是全表最严重的问题，理由不是它自身破坏力最大，而是它使其余所有问题不可观测、不可验证。

损失形态：不是一次性爆炸，而是持续性的效率税。一个 5 人团队缺失评测，保守估计浪费 30–50% 的迭代产能，且这部分浪费在财报上完全不可见——没有事故报告，没有停机记录，只有"我们一直很忙但没什么进展"。

恶化机制（本文强调的关键点）：评测成本高 → 评测频次低 → 漂移累积 → 需要更大的评测集才能定位 → 成本更高。这是正反馈环，越晚建成本越高。它是本文所有问题中唯一具有明确"债务复利"特征的一项。

2.3 理论基础：开环系统的期望收益为零

控制论第一性原理：没有反馈信号的系统不是控制系统，是开环系统。开环系统的迭代等价于随机游走，期望改进量为 0。

这是"不断换框架换模型但效果原地踏步"现象的严格解释——不是收益小，是数学上为零，因为系统无法区分改进与噪声。

求解理论包含四个组件：

（1）评测集是系统的传递函数标定[8]

必须从线上真实分布采样[9]，而非人工构造。离线分布与线上分布的 KL 散度决定了指标的失效程度。人工编造的 100 条 case 看起来像评测集，但如果它们的分布与真实流量相差甚远，优化它们等于优化一个不存在的系统。

（2）分层评测：级联过滤器[10]

按成本递增排列三层：

  • 确定性断言层（schema / 格式 / 引用存在性）→ 成本近零，先跑
  • 规则与程序化检查层（数值正确性、关键词、工具调用序列）
  • 模型评判层（LLM-as-judge）→ 成本高，最后跑

设计目标是让 90% 的回归在前两层被廉价拦截。这直接攻击"评测成本高导致频次低"这一恶化机制的根部。

（3）对 judge 本身做元评测[11]

judge 是测量仪器，必须校准。用人工标注集测 judge 与人类判断的一致性（Cohen's κ）。κ < 0.6 的 judge 产出的指标不可用——此时你测的是 judge 的偏好，不是系统的质量。

（4）Goodhart 防御[12]

"当指标成为目标，它就不再是好指标。"对策是保持一个从不用于优化的 holdout 集，定期换血。任何长期用于调优的评测集都会被过拟合，这是统计学的必然而非团队的过失。

2.4 收益结构

这是全栈最高杠杆的投入：

  • 迭代从随机游走变为梯度下降：每次改动有方向，无效改动被当场拒绝，研发有效产出率通常提升 2–3 倍
  • 解锁一切其他优化：降本、换模型、改 RAG、精简 prompt 全部变得"敢做"，因为有安全网。这一点常被低估——评测的最大价值不是发现退化，而是让激进优化成为可能
  • 决策去政治化：「用哪个模型」「谁的 prompt 更好」由数据裁决，减少团队内耗
  • 上线门槛可自动化：评测入 CI 后，质量把关不再依赖人工抽查

投入产出：100–300 条黄金集，2–3 人周建设，通常在第一次模型升级时即回本。

量化指标：黄金集通过率、变更前后 Δ 分、评测覆盖的线上流量占比、发布回滚率

第三章 供应商锁定与模型版本治理

3.1 问题机理

模型是会自行变化的外部依赖——这是传统软件工程中不存在的依赖类别。库的版本不会自己改变行为，但模型会：

  • 模型弃用（deprecation）是强制变更，业务必须被动迁移
  • Prompt 对特定模型过拟合，换模型即效果塌陷
  • 能力边界随版本变化，但接口签名不变，故障是静默的
  • 多模型路由虽能缓解锁定，却把一致性问题放大到 N 倍

3.2 严重性评估

维度评估
影响面L2–L4
可逆性中（迁移可行但昂贵，3–6 人月量级）
发生概率高（模型弃用是确定事件，只是时间问题）
检测难度高——接口不变 + 故障静默是最恶劣的组合
综合等级High（P2，但具有"定时炸弹"属性）

它的危险不在日常，而在时间点不由你决定。模型弃用是供应商单方面的强制变更，会在任意时刻把一个 P2 问题瞬间升级为 P0 的紧急迁移项目，且往往与业务高峰期重叠。

最恶劣的子问题是"静默故障"：版本升级后接口签名不变、HTTP 200、返回格式合法，但能力边界变了——某类 case 的准确率从 92% 掉到 74%，而监控系统全绿。这类故障的平均发现周期是周级到月级，中间产生的错误输出已全部交付给用户。

缓解措施的反噬：多模型路由是常见解法，但它把"一个模型的不一致"变成"N 个模型的不一致"，评测矩阵从 1 维变 N 维。在评测体系建成前引入多模型路由，是净负收益。

3.3 理论基础：依赖倒置、反腐层与期权定价

（1）依赖倒置原则（DIP）[13]

业务代码应依赖自定义抽象（Summarizer 接口）而非供应商 SDK（openai.chat.completions）。抽象的所有权在你手上，供应商变更被限制在适配层内。

（2）反腐层（Anti-Corruption Layer, DDD）[14]

网关层做语义归一化——统一错误码、统一 token 计量、统一工具调用格式、统一流式协议。业务代码永远不感知供应商差异。

（3）语义版本锁定 ≠ 字符串版本锁定[15]

这是本章最重要的理论点。锁定模型 ID 字符串给人虚假的安全感。真正的版本锁定是一个四元组快照：

{模型 ID, prompt, 参数, 评测基线}

迁移的验收条件不是"接口能跑通"，而是新四元组在同一评测集上不劣于旧基线。这把迁移从"工程任务"变成"可判定的验收问题"。

（4）多模型路由的一致性代价[16]

路由把系统从单一分布变成混合分布，方差上升。理论上应按"能力等价类"分组路由——只在同一等价类内路由，跨类需独立评测基线。否则一致性问题按 N 倍放大。

（5）期权视角[17]

维护第二模型的可用性是一份看跌期权：

  • 权利金 = 双份评测与适配成本
  • 行权收益 = 弃用/涨价/降质时的切换能力

这让"要不要做多模型"从信仰之争变成可算的决策。当供应商集中度高、迁移成本大时，权利金值得付；当业务尚小、评测未建时，权利金过高。

3.4 收益结构

  • 迁移成本从项目级降为配置级：弃用公告来临时，从"6 周迁移专项"变成"跑一次评测 + 改配置"
  • 议价能力：可随时切换供应商，从被动接受涨价变为可比价，长期 API 成本下降空间通常 20–40%
  • 静默故障显性化：版本变更触发评测告警，能力退化在上线前被发现
  • 可做能力分层：简单任务走小模型、难任务走大模型，兼得成本与质量

关键执行建议：优先级 P2 合理，但必须预置逃生通道（统一网关 + 内部抽象接口），而不是等到弃用公告发出再动工。缓解成本前置很低，后置很高——这是典型的期权式投资。

第四章 成本不可预测与归因缺失

4.1 问题机理

成本模型为 C = Σ tᵢ·pᵢ，其中 token 量 tᵢ 由用户输入与 Agent 迭代轮数决定——本质上不由系统控制。具体表现：

  • Agent 的循环调用造成成本尾部爆炸（一次异常会话消耗上千次调用）
  • 缓存命中率、上下文裁剪策略直接决定单位成本，但常被忽视
  • 缺少按功能/租户/请求的成本归因，无法做单位经济性核算

4.2 严重性评估：必须分场景

维度评估
影响面L3–L6 + 商业模型
可逆性高（成本可止损，不产生永久损害）
发生概率高
检测难度中（账单会说话，但滞后一个计费周期）
综合等级High（P1），Agent 场景下升级为 Critical

这是本文中场景差异最大的一项：

  • 纯对话 / 单次调用场景：等级 Medium。成本与请求量线性相关，可预测性尚可，最坏情况有界。
  • Agent 场景：等级 Critical。成本分布是长尾且无上界的——一次进入循环的异常会话可以消耗上千次调用。这不是"贵一点"，而是单个请求即可击穿日预算。更严重的是它可被恶意触发，构成一个经济型 DoS 面（攻击者只需构造诱发长循环的输入，无需任何漏洞利用）。

"难归因"的真实代价：无法按功能/租户核算单位成本 → 无法判断哪个功能是亏损的 → 定价决策失去依据。对 B2B SaaS 而言这直接威胁商业模型的成立，而非仅仅是运维问题。

4.3 理论基础：重尾分布下的截断优于预测

（1）硬闸门优于软预测[18]

这是本章的核心理论。在重尾分布下，均值由尾部主导，因此"平均成本"这个统计量本身是误导性的，基于它的预测与容量规划全部失真。

正确的做法不是更精确地预测，而是直接截断分布：会话级 token 上限、工具调用轮数上限、单请求超时。截断把无界期望变成有界期望——这是唯一可靠的成本控制手段。

（2）成本归因需要维度化计量[19]

每次调用打标签（租户 / 功能 / 请求 ID / 模型 / 缓存命中）。没有维度就无法计算真正该优化的指标：cost per successful task，而非 cost per call。二者的区别至关重要——降低单次调用成本但导致失败重试，总成本反而上升。

（3）缓存的理论地位：一条架构约束[20]

Prompt 缓存把成本从 O(n) 降到 O(Δ)，前提是前缀稳定。由此推导出一条硬性架构约束[21]：上下文必须按「稳定 → 易变」排序：

系统提示 → 工具定义 → 知识 → 对话历史 → 当前输入

这不是调优技巧，而是由缓存机制推导出的结构性要求。任何把易变内容（时间戳、用户 ID）放在前缀的设计，都会整体摧毁缓存收益。

（4）成本-质量帕累托前沿

每个任务应定位在前沿上。简单任务用小模型不是"省钱"，是消除浪费；复杂任务用小模型导致的重试会让总成本更高——这是前沿之外的劣解，两头都输。

4.4 收益结构

  • 尾部风险被截断：这是风险消除型收益，不是优化型收益。会话级硬上限直接消除"一次异常会话烧掉上千次调用"的成本事故
  • 单位经济性可算：知道每个功能、每个租户、每次请求的成本，才能定价、才能判断某功能是否该下线
  • 优化有靶子：缓存命中率、上下文裁剪、模型分层的收益可被量化，典型可降 30–60% 推理成本
  • 预算可预测：财务从"月底看账单惊吓"变为"容量规划"

量化指标：每请求成本、每活跃用户成本、缓存命中率、成本 P99/P50 比值、毛利率

本章的执行结论：token 与轮数上限是几十行代码的事，却能把"无上界风险"变成"有界成本"。这是全文投入产出比最高的单项措施，应当立即执行，不需要等待任何前置条件。

第五章 延迟与上下文的结构性张力

5.1 问题机理

  • 上下文越长效果越好、延迟与成本越高，且存在「中间遗忘」现象
  • RAG 检索、重排、生成串行叠加，P99 延迟远高于均值
  • Agent 多轮串行使延迟从秒级升到分钟级，交互体验被迫改为异步

5.2 严重性评估：一个被高估的问题

维度评估
影响面L3–L4 + 产品形态
可逆性高
发生概率100%
检测难度低（延迟是传统监控的强项）
综合等级Medium ↓

这是全文中最被高估的问题之一，理由有三：

  1. 它高度可见——P99 延迟是成熟监控体系的标准指标，不会静默恶化
  2. 它不产生错误输出——慢，但是对的
  3. 它有明确的产品级解法——把交互改成异步（流式输出、任务队列、进度反馈），用户接受度远比工程师预期的高

但必须拆出一个子项重新归类。「中间遗忘」（lost in the middle）实际上不属于延迟问题，而是质量问题被错误分类。长上下文中位置靠中间的关键信息被忽略，表现为"模型没看到我给的资料"，且不会体现在任何延迟指标上。它应移至第六章（上下文与检索工程）下处理，等级 High。

这是一个值得读者注意的方法论要点：问题分类错误本身就是一种系统性风险——被归入 Medium 类目的 High 级问题，会因为类目优先级而被长期搁置。

5.3 理论基础：Amdahl 定律与信息瓶颈

（1）Amdahl 定律[22]

延迟由串行链决定：L = ΣL_serial + max L_parallel。RAG + 重排 + 生成是纯串行链，因此优化非瓶颈环节收益趋零。

工程推论：凡是不存在数据依赖的步骤必须并行——检索与候选生成并发、多路检索并发、推测性预取。这是延迟优化的第一性手段，优先于任何单环节的微调。

（2）上下文的信息瓶颈原理[23]

目标不是"塞更多"，而是在保留任务相关信息 I(X;Y) 的前提下最小化 |X|。

这条原理有一个直接且违反直觉的推论：重排（rerank）的价值高于扩大 top-k。前者提升信息密度，后者稀释它。扩大 top-k 在增加成本与延迟的同时，还可能因引入噪声而降低质量——三重损失。

（3）"中间遗忘"是位置偏置的必然结果[24]

工程推论直接可执行：关键信息必须置于上下文首尾，中段放低优先级内容。这是一条布局规则，不需要任何模型能力提升即可生效。

（4）P99 治理与感知延迟[25]

用户体验由 P99 而非均值决定。对策是分层响应——流式首 token、中间态展示、长任务转异步 + 通知。这把"降低延迟"的不可能任务，转化为"降低感知延迟"的可能任务。

5.4 收益结构

  • 转化率与留存直接提升：交互式场景延迟每降 1 秒，完成率提升显著；P99 收敛比均值优化更影响体感
  • 成本与延迟同步改善：上下文裁剪同时降低 token 与首字延迟，一举两得
  • 架构选择变清晰：明确哪些场景必须同步（对话）、哪些应改异步（长任务），产品形态设计不再被技术误导
  • 绕开"中间遗忘"：精简上下文往往同时提升准确率——质量与性能在此处非零和

量化指标：TTFT、端到端 P50/P95/P99、平均上下文长度、任务完成率

资源配置建议：延迟部分不应占用 P0/P1 资源；但"中间遗忘"需拆出提升至 High。

第六章 RAG 与数据管线的隐性债务

6.1 问题机理

  • 检索质量（召回、分块、重排）通常是效果瓶颈，但归因常被错判为"模型不行"
  • 知识库更新、失效、权限过滤缺乏机制，产生"陈旧答案"与"越权泄露"
  • Embedding 模型升级需要全量重建索引，代价高且缺少灰度手段
  • 多源数据的清洗与去重缺失，噪声直接进入答案

6.2 严重性评估：必须拆分为三个不同等级

维度评估
影响面L4–L5
可逆性权限泄露不可逆；其余可逆
发生概率高
检测难度高（归因常被错判）
综合等级需拆分处理

将本章问题合并为单一等级是危险的。必须拆成三项：

6a. 检索质量（召回、分块、重排）—— High

真实的效果天花板通常在这里，但归因错误率极高：团队观察到"回答不准"，第一反应是换更大的模型或改 prompt，而真实原因是召回率只有 60%。这导致大量工程投入打在错误的位置上。讽刺的是，诊断方法其实很便宜——人工检查 50 条 case 的检索结果即可定位——但因为缺少这个习惯而被长期忽视。

6b. 权限过滤缺失导致越权泄露 —— Critical ↑↑

这不是 RAG 质量问题，而是安全事故，被埋在"隐性债务"标题下严重低估。一旦 A 部门用户通过检索拿到 B 部门的机密文档，损害具有三个特征：

  • 不可逆（信息已被读取，无法撤回）
  • 外部化（触发合规与法律责任，损失不由工程团队承担）
  • 批量性（一个错误的索引配置影响全部查询，而非单次失误）

它应当与第八章合并，进入 P0。

6c. Embedding 升级需全量重建索引 —— Medium ↓

成本高但可计划、可预算、无突发性。属于运维负担而非风险。

6.3 理论基础：误差归因分解与安全边界前移

（1）误差分解决定投资方向

端到端质量可分解为 Q = f(召回, 精度, 生成)。若检索召回率为 0.6，则无论生成模型多强，质量上界就是 0.6。

这是"换更强的模型常常无效"的严格解释——瓶颈不在那一层，提升非瓶颈环节不改变系统上界。

（2）分层独立评测是归因的前提[26]

具体方法：

  • 单独测检索：Recall@k、MRR、nDCG
  • 单独测"给定正确上下文时的生成质量"

两个数一出，瓶颈立刻确定，不再靠猜。这是本章成本最低、收益最高的单项实践。

（3）分块是信息单元设计问题，不是参数调优[27]

理论准则：一个 chunk 应是语义自足的最小单元——脱离上下文仍可独立回答问题。按结构（标题/段落/表格）分块优于按固定长度切分。把分块当作调 chunk_size=512 的超参搜索，是把设计问题误认为调优问题。

（4）索引即缓存，必须有失效策略[28]

陈旧答案的本质是缓存一致性问题，解法直接沿用经典缓存理论：TTL、写时失效、版本号。把它当作"数据管线不够勤快"是误诊。

（5）权限必须在检索层过滤，不能在生成层[29]

理论依据：生成层无法可靠执行否定约束（"不要提到 X"）。一旦信息进入上下文，即应视为已泄露——因为模型可能复述它、可能被诱导复述它、可能在摘要中间接透露它。

因此安全边界必须前移到数据获取点：检索时就不返回无权限的文档。这是一条不可让步的架构原则。

（6）Embedding 升级的灰度：扩张-收缩模式[30]

双写双索引 + 影子查询对比，这是标准的 expand-contract 迁移模式，把不可回滚的全量重建变成可回滚的渐进切换。

6.4 收益结构

  • 归因正确：区分"检索没召回"与"模型没答对"。实践中多数"模型不行"实为检索问题，修检索的 ROI 远高于换模型——且成本几乎不变
  • 效果天花板抬升：召回率提升直接转化为答案正确率
  • 消除陈旧与越权两类高危错误：后者是合规级风险
  • 升级可控：索引重建有灰度与回滚，embedding 升级不再是高危操作

量化指标：Recall@k、检索命中率、答案可溯源率、知识陈旧度、越权检索次数（目标为 0）

第七章 Agent 层的可靠性放大效应

7.1 问题机理

  • 单步 95% 正确率，十步串联只剩 60%，误差按乘法衰减
  • 缺乏中断、回滚、幂等与人类审批点，副作用操作风险高
  • 工具描述即接口契约，却没有版本管理与兼容性测试
  • 失败模式多为"看似成功的错误"，比崩溃更难发现

7.2 严重性评估：一个准入问题，不是优先级问题

维度评估
影响面L4，但通过工具调用外溢到外部系统
可逆性低——副作用操作（发邮件、改数据库、下订单）不可撤销
发生概率中（取决于是否已上 Agent）
检测难度极高——"看似成功的错误"是最难检测的故障形态
综合等级条件性 Critical

这是全文等级跨度最大的一项，完全取决于是否具备副作用权限：

  • 只读 Agent（检索、分析、总结）：等级 Medium。错了就是答案不对，与普通质量问题同级。
  • 有写权限 / 能触发外部动作的 Agent：等级 Critical。误差乘法衰减（0.95¹⁰ ≈ 0.60）意味着十步任务有 40% 概率出错，而其中一部分错误会以真实世界的不可逆操作形式落地。

最危险的特征是"看似成功的错误"：Agent 报告"任务已完成"，日志显示每一步都返回成功，但实际执行的是错误的操作。这种故障同时躲过了错误率监控和用户即时感知，可能在数周后才通过下游数据异常被发现。相比之下，崩溃是良性故障——它至少会告诉你它失败了。

依赖关系：本项的治理强依赖第九章（可观测性）。没有全链路 trace，Agent 事故根本无法复盘——你只能看到一个"成功"的结果和一个错误的世界状态，中间的十步推理链已经丢失。

本文的核心修订：将 Agent 可靠性列为 P3 在只读场景下成立，在有写权限场景下是严重误判。正确的框架不是排优先级，而是设准入门槛：

判断标准：Agent 能否触发不可逆操作？能，则 P0；不能，则 P3。
在 trace 与人类审批点就位之前，不应授予 Agent 写权限。

7.3 理论基础：冯·诺依曼的答案

串联可靠性 R = Π rᵢ。当 r = 0.95、n = 10 时 R ≈ 0.60。这是乘法衰减，不可能靠提升单步精度线性解决——要达到 0.95 的十步总成功率，单步需达到 0.995。

冯·诺依曼在《用不可靠元件构造可靠系统》中给出的答案是：冗余 + 纠错。具体到 Agent：

（1）减少 n：步数是可靠性预算[31]

最有效的手段是缩短链路。能用确定性代码做的步骤绝不交给模型——每替换一步，可靠性提升一个因子。Agent 的步数是可靠性预算，必须吝啬支出。这一条与直觉相反：更"智能"的多步 Agent 往往比"笨"的固定流水线更不可靠。

（2）加入纠错环[32]

每步后验证（校验输出 schema、检查工具返回、断言前置条件），失败即重试。这把串联单步可靠性从 r 提升为 1-(1-r)^k，是唯一能在结构上突破乘法衰减的手段。

（3）Saga 模式治理副作用[33]

每个有副作用的步骤必须定义补偿操作；所有工具调用必须幂等（带幂等键）。这样失败时可回滚到一致状态，而非留下半完成的烂摊子。

（4）不信任自报成功[34]

针对"看似成功的错误"：验证必须来自外部可观测状态（查数据库确认记录已写入），而非模型的自我声明。模型说"我已完成"在证据等级上等同于无证据。

（5）工具描述即 API 契约[35]

需要版本管理、向后兼容、变更评审。工具描述的一次措辞改动可能改变整个 Agent 的行为分布——其风险等级等同于生产代码变更，却常被当作文案调整随手提交。

（6）人类审批点设在不可逆操作前

这是把「概率性决策」与「不可逆后果」解耦的唯一可靠手段。它不提升成功率，但把失败的性质从"灾难"改为"被拦截的事件"。

7.4 收益结构

  • 误差乘法衰减被打断：加入每步校验与重试后，十步任务成功率可从 ~60% 回到 85%+，这是 Agent 能否商用的分水岭
  • 副作用可控：幂等 + 回滚 + 审批点，把"Agent 误删数据"从灾难变成可拦截事件，是开放写权限的前提条件
  • "看似成功的错误"被捕获：结构化结果校验让静默错误显性化，这类错误的业务危害远大于崩溃
  • 工具契约稳定：工具描述版本化后，新增工具不再打破既有能力

量化指标：端到端任务成功率、每任务平均步数、静默错误率、需人工介入率、回滚成功率

第八章 安全与信任边界

8.1 问题机理

  • Prompt 注入无法根治，模型无法可靠区分"指令"与"数据"
  • 检索内容与工具返回值均为不可信输入，却常被直接拼入上下文
  • 权限模型错位：应按用户鉴权，实践中常按 Agent 身份鉴权，导致越权
  • 输出侧的敏感信息泄露与幻觉外溢缺少统一护栏

根本困难的架构定位[36]：LLM 的输入是单一未分型的 token 流，指令与数据在同一通道。这在架构上等同于冯·诺依曼体系的代码/数据同址——因此 prompt 注入与缓冲区溢出同源，不可能在模型层面根治，只能在架构层面围堵。

8.2 严重性评估

维度评估
影响面全栈
可逆性不可逆（数据泄露无法撤回）
发生概率中高（注入尝试是必然的，成功率取决于防护）
检测难度高
综合等级Critical（P0）

本章与第二章并列最高优先级，但性质完全不同——第二章是持续性效率损失，本章是低频但不可逆的灾难性事件。

方法论警告：用期望值衡量二者会得出错误结论。安全问题的正确衡量方式是最坏情况（worst case），而非期望损失。一个"每年 2% 概率、损失 5000 万"的风险，其期望值看似可接受，但若该损失足以终结业务，期望值就是错误的决策函数。

分项严重性（本章内部必须重排）：

8a. Prompt 注入 —— High ↓

需要正确认知：它在架构层面无法根治。模型无法可靠区分指令与数据，这是与第一章同源的结构性缺陷。因此目标不能是"防住注入"，而只能是"限制注入成功后的爆炸半径"。任何承诺"彻底解决 prompt 注入"的方案都应被怀疑。

8b. 权限模型错位 —— Critical，且是本章中最应优先修复的

理由：它是确定性缺陷而非概率性缺陷，因此可以被彻底修复。一个以服务账号身份访问全量数据的 Agent，等价于给每个用户开了管理员权限。这不需要攻击者构造精巧的注入——一个普通用户提出一个越界问题就够了。

8c. 检索内容与工具返回值被直接拼入上下文 —— High

这是注入的主要载体，且常被忽视，因为团队只防"用户输入"，不防"自己系统内部"的数据。而知识库文档、网页抓取结果、第三方 API 返回值全部是不可信输入。

8.3 理论基础：信息流控制与混淆代理

（1）污点追踪（taint tracking）[37]

所有非可信源（检索内容、工具返回、用户输入、网页）标记为 tainted。系统必须保证一条不变量：

tainted 数据不得直接决定特权操作。

这条不变量是可形式化验证的，这使它区别于"小心一点"式的建议。

（2）能力与数据分离[38]

模型决定"做什么"，但"能做什么"由外部权限系统决定。执行层必须独立于模型重新鉴权——模型的输出是请求，不是授权。

（3）混淆代理问题（Confused Deputy）[39]

Agent 以自身身份鉴权就是经典的混淆代理——它持有比调用者更高的权限并代其行事。

正解是权限传递（credential propagation）：Agent 执行操作时使用发起用户的凭证，而非服务凭证。这一条能消除绝大多数越权，且实现路径明确、成本有限。

（4）Dual LLM 模式[40]

  • 一个特权 LLM：从不接触不可信数据，只做调度
  • 一个隔离 LLM：处理不可信数据，但无任何工具权限
  • 两者之间只传结构化数据

这是当前对 prompt 注入唯一有理论保证的架构。代价是复杂度上升，适用于高价值场景。

（5）深度防御[41]

输入侧结构化包裹、输出侧敏感信息扫描、执行侧审批。任何单层防御都会被绕过，必须叠加。

（6）不对称性原则[42]

安全事故不可逆且外部化（合规罚款、用户信任流失），而防御成本可逆。因此在期望损失计算上，安全应当过度投资——这是不对称收益下的正确策略，而非保守主义。

8.4 收益结构

  • 不可逆风险转为可控风险：建立边界是买保险而非性能优化，收益 = 避免的损失
  • 解锁高价值场景：只有权限模型正确（按最终用户鉴权），才敢把 Agent 接入 CRM、财务、生产数据库——这是商业价值最大的场景
  • 合规准入：满足审计要求后，才能进入金融、医疗、政企等高客单市场
  • 信任即采纳率：护栏到位后内部使用率上升，因为员工敢用

量化指标：注入攻击拦截率、越权访问数（目标 0）、敏感信息外泄检出、红队通过率

本章执行结论：Critical、P0 无争议，但内部必须重排——先修权限模型（可根治、投入明确），再做注入缓解（只能减损、投入无底）。把两者平铺处理，会导致资源投向收益递减的那一侧，同时放着一个几天就能修好的越权漏洞不管。

第九章 可观测性断层

9.1 问题机理

  • 传统 APM 只看延迟与错误率，看不到"回答质量"
  • Trace 缺少 prompt / 上下文 / 中间步骤的完整记录，事故无法复盘
  • 日志包含用户数据，与隐私合规冲突，导致"该记的不敢记"
  • 缺少线上质量的实时信号（用户反馈、拒答率、重试率）

9.2 严重性评估

维度评估
影响面全栈
可逆性中（历史数据一旦未采集则永久丢失）
发生概率高
检测难度高（元问题：缺少观测能力就无法观测到自己缺少观测能力）
综合等级High（P1），Agent 场景下为 Critical 前置条件

本章的严重性几乎全部是间接的——它自身不制造故障，但它决定其余所有故障能否被定位。

它与第二章构成一对：评测负责"上线前知道好不好"，可观测负责"上线后知道哪里坏了"。缺任何一个，另一个的价值都会减半。

不可逆的部分值得单独强调：trace 未采集的历史请求永久无法补录。这意味着今天不建设，明天发生事故时没有任何历史基线可供对比——你无法回答"这个问题是新出现的，还是一直存在只是没人发现"。这一点使它比大多数 P1 问题更紧迫。

最棘手的子问题：隐私合规与可观测性直接冲突。trace 必须包含 prompt 和上下文才有诊断价值，而这些恰恰含有用户数据。"该记的不敢记"是真实困境，且没有免费解法——脱敏会降低诊断价值，不脱敏则违规。这需要产品、法务、工程三方共同决策，不是纯技术问题，因此常常被无限期搁置。这是它在实践中经常烂尾的根本原因。

9.3 理论基础：卡尔曼可观测性

（1）可观测性的严格定义[43]

系统可观测，当且仅当能从输出序列唯一重建内部状态。

传统 APM 只记录延迟与状态码，而 AI 系统的内部状态是「上下文内容 + 中间推理 + 工具序列」[44]——这些不记录，系统就是不可观测的，事故永远无法复盘。这不是"日志不够详细"的程度问题，而是数学意义上的能力缺失。

（2）完整 Trace 是状态重建的必要条件[45]

必须记录：prompt 全文、检索结果、每次工具调用的入参与返回、token 与成本、模型版本。

判据极其简单：能否仅凭日志离线重放这次会话？ 不能，就是不可观测。这个判据的好处是它不可自欺——团队无法用"我们有日志"搪塞过去。

（3）质量信号必须与系统信号并列[46]

可观测的质量代理指标：拒答率、重试率、用户编辑率、会话轮数、点踩率。

它们是先导指标，早于离线评测发现线上退化。系统指标全绿而质量指标恶化，正是第三章"静默故障"的检测手段。

（4）隐私冲突的解法是分级而非放弃[47]

三级策略：

  • 全量记录结构化元数据（无内容）
  • 采样记录脱敏后的内容
  • 短 TTL 的原始内容

用差异化保留期同时满足复盘需求与合规要求。"该记的不敢记"是伪两难——它之所以看起来无解，是因为被当作二元选择（记 or 不记）而非分级设计。

（5）Trace 是评测集的供给管线[48]

这一条闭环最关键：可观测性不只服务于排障，它是第二章黄金集的数据来源。线上 trace 采样脱敏后直接进入评测集，二者是同一基础设施的两个出口。

理解这一点会改变投资决策：trace 与评测不应作为两个项目分别立项排期，而应作为一套设施一次建成。

9.4 收益结构

  • 让其余问题变得"可解"：成本归因、检索归因、Agent 失败分析全部依赖它——它是其他治理项的前置基础设施
  • 事故复盘从猜测变为回放：记录 prompt、检索结果、每步调用后，可精确还原现场
  • 线上质量有实时信号：拒答率、重试率、负反馈率构成质量早期预警，不必等评测周期
  • 评测数据自动增长：线上 Trace 采样脱敏后喂给黄金集，评测体系自我强化，形成飞轮

量化指标：Trace 覆盖率、MTTR、线上负反馈率、评测集来自真实流量的比例

第十章 组织与流程：被低估的元问题

10.1 问题机理

  • 算法、后端、产品三方对"什么叫做好了"缺乏共同定义
  • Prompt 散落在代码、配置、数据库中，无版本、无评审、无发布流程
  • Demo 到生产的鸿沟：原型 2 周，生产化 6 个月，预期严重错配
  • 技术栈迭代快于团队沉淀速度，框架选型频繁推倒重来

10.2 严重性评估

维度评估
影响面全部人员与全部技术决策
可逆性低（组织惯性的改变周期以季度计）
发生概率极高
检测难度中（症状明显，根因常被否认）
综合等级High（元问题，实际驱动前九章的存废）

这是最容易被工程团队低估的一项，因为它不表现为技术故障，而表现为"我们一直很忙但没什么进展"。

分项评估：

10a. 三方对"做好了"缺乏共同定义 —— Critical（元级）

这是第二章的真正上游。评测体系建不起来，往往不是因为技术难，而是因为没有人能说清什么叫做对。跳过这一步直接建评测，只会产出一个没人认可的指标——算法认为通过了，产品认为没解决问题，后端不知道该拦什么。这条是整篇分析中最深的根因。

10b. Prompt 散落无版本管理 —— High

它使故障不可复盘（不知道上周跑的是哪一版）、使回滚不可能，且修复成本极低（进 git、加 owner、走评审，一周内可完成）。这是典型的高收益低成本项，被长期拖延纯粹因为不紧急。

10c. Demo 到生产的鸿沟 —— High

危害是期望错配导致的资源误配：管理层看到 demo 后按 demo 的速度分配预算与排期，工程团队则在生产化阶段被迫牺牲的恰恰是评测、可观测、安全这些"看不见"的部分。这条是前九章问题的共同制造机制——不是团队不知道该建评测，而是排期里没有它的位置。

10d. 框架选型反复推倒重来 —— Medium

看似浪费，但在技术快速演进期部分重构是合理成本。真正的问题是换框架常被当作解决效果问题的手段，而效果问题的真因在评测缺失和 RAG 质量上——换框架只是换了个地方原地踏步。

10.3 理论基础：康威定律与资产化

（1）康威定律[49]

系统架构会复制组织沟通结构。算法、后端、产品三方对"做好了"没有共同定义，系统边界必然在这三者之间断裂——前九章的许多症状，是这条组织裂缝的技术投影。

（2）用评测集作为共同语言[50]

评测集把"好"这个主观词编码成三方都能读懂的可执行对象。它同时是：

  • 产品的验收标准
  • 算法的优化目标
  • 后端的回归门禁

一个物件，消除三方定义分歧。 这是第二章 P0 优先级的真正理由：它既是技术基础设施，也是组织协调机制。只从技术角度理解评测，会低估它一半的价值。

（3）Prompt 是源代码，不是配置[51]

它决定系统行为、需要评审、需要版本、需要灰度、需要回滚。散落在数据库和硬编码里的 prompt 等同于无版本控制的生产代码——这在传统工程里不可接受，在 AI 工程里同样不可接受。把 prompt 归类为"配置"，是导致治理缺位的分类错误。

（4）Demo-生产鸿沟的理论解释[52]

原型只需覆盖 happy path（输入空间的极小子集），生产需要覆盖长尾。而 LLM 系统的长尾比传统软件长得多——输入是自然语言，空间无界。

因此 2 周到 6 个月的比例不是执行力问题，是问题本质。正确的做法是在预期管理上明确：Demo 完成度 ≈ 5%，而非 80%。这个数字应该在 demo 演示的同一场会议上说出来。

（5）框架选型的抗脆弱策略[53]

把易变的（框架、模型、SDK）放在适配层，把稳定的（评测集、Trace 数据、业务逻辑、领域知识）放在核心。换框架时资产不损失。

判断标准是一个问题：换掉框架 X，我会损失什么？ 损失越大，耦合越需要切断。

10.4 收益结构

  • "做好了"有共同定义：评测指标成为三方共同语言，验收争议大幅减少
  • Prompt 资产化的复利：进版本库 + 有 owner + 可 diff + 可灰度回滚后，知识沉淀在组织而非个人，人员流动不再造成能力丢失
  • 预期对齐：明确鸿沟来源，避免向上承诺失真导致的信任透支
  • 选型稳定：有了内部抽象层与评测，框架更换成为可评估的局部决策，而非推倒重来

量化指标：需求返工率、Prompt 变更平均发布时长、原型到生产周期、关键人依赖度

本章结论：前九章的技术问题，大部分是本章的症状而非独立病因。纯技术投入无法解决"没人定义什么叫做对"。

第十一章 收敛：依赖偏序与投入顺序

11.1 依赖关系图[54]

组织共识（什么叫做对）
      │
      ▼
可观测性 (Trace) ──→ 评测集 ──→ 一切改进的可验证性
      │                 │
      ├──→ 成本归因 ──→ 成本闸门
      │
安全边界 ──→ 独立于上述，但不可逆，故并列 P0
      │
      └──→ Agent 可靠性工程（依赖上述全部就位）

11.2 修订后的投入顺序

定义验收标准（组织）→ 建评测与 trace（测量）→ 修权限模型与成本闸门（约束）→ 治理 RAG 与模型版本（质量与迁移）→ 放开 Agent 写权限（能力）

"先测量约束、再能力增强"的方向是正确的；本文的贡献是在其前面补上缺失的第零步（组织共识），并把三个被埋在低优先级里的 Critical 项提了出来：检索层越权、Agent 写权限、Agent 成本上界。

11.3 收益结构的四种类型

收益类型对应问题性质
风险消除（不可逆）安全边界、成本闸门、Agent 副作用买保险，收益 = 避免的损失
能力解锁（前置条件）评测、可观测性本身不产生价值，但决定其他投资能否兑现
效率提升（可累积）模型治理、RAG、延迟优化复利型，越早建设收益越大
组织沉淀（长期）流程与资产化抗人员流动，决定长期速度

混淆这四种收益类型是常见的决策错误：用"能带来多少提升"去衡量安全投入，会永远得出"不划算"；用"期望损失"去衡量成本闸门，会低估尾部风险。

11.4 三点关键结论

1. 最大的优先级误判在 Agent 可靠性。 把它排在 P3，对"只读 Agent"成立，但对"有写权限的 Agent"是危险的低估。正确的框架不是排优先级，而是设准入门槛：trace 与人类审批点就位之前，不授予 Agent 副作用权限。

2. "安全"被过度合并，导致资源投向错误的一侧。 权限模型错位是确定性缺陷、可彻底修复、投入有限；Prompt 注入是结构性缺陷、只能减损、投入无底。二者平铺处理，会让团队把精力花在收益递减的注入防护上，而放着一个几天就能修好的越权漏洞不管。

3. 真正的根因比"评测缺失"更靠上一层。 评测建不起来，通常不是技术问题，而是组织内部对"什么叫做对"没有共识。

11.5 终论

AI Engineering Stack 的核心矛盾在于：用概率性组件搭建确定性产品。

其绝大多数故障不是"模型不够强"，而是缺少把不确定性约束住的工程设施——评测、可观测、成本闸门、安全边界。这些设施的共同特征是：它们自身不创造可演示的价值，因此在 demo 驱动的资源分配中系统性地被排在后面；而它们又恰恰是判断其他一切投资是否有效的唯一通道。

因此投入顺序应当是先建「测量与约束」，再做「能力增强」。反序推进的必然结局，就是那个熟悉的循环：不断更换框架与模型，效果原地踏步。

这不是执行不力，而是开环系统的稳态行为。
