一他说的是什么

Hashimoto 的定义可以压成一句话:凡是发现 agent 犯了某个错,就花时间去 engineer a solution such that the agent never makes that mistake again。 —— Mitchell Hashimoto,《My AI Adoption Journey》,2026-02-05

他明说自己不确定业界有没有通行叫法,是自己长期这么叫的。而他给的落地手段只有两种:

他说的形式做什么他给的适用范围
更好的隐式提示(AGENTS.md 之类) 把「agent 老是跑错命令、找错 API」这类毛病写成一行规矩 他原话限定在 simple things
真正编出来的工具 截图脚本、过滤过的测试等等,并在 AGENTS.md 里告诉 agent 它存在 他把「最可靠的办法」这句话给了这一类:
让 agent 能自动知道自己错了

注意他的排序:提示只管简单毛病,能自动说「你错了」的工具才是主力。这一点马上要用到。

二把他的两种形式,接到 #176 量出来的四层上

上一张卡(#176)我量过这条流水线的不变量都由谁来拦,结论是四档。 把 Hashimoto 的两种形式贴上去,正好只覆盖其中两档 —— 而剩下两档才是熵的漏口:

第一档
代码拦 = 他说的「真正编出来的工具」 违反时会炸(ImportError、断言失败)。熵增速度 0 —— 不可能悄悄退化,语言替你盯着。
第二档
Schema 拦 = 他没单列,但同属「工具」 JSON Schema 在 tool-call 层强制,不合规模型重试。熵增极低,而且是唯一对 LLM 直接生效的硬约束。
第三档
提示词说说 = 他说的「隐式提示」 违反了没有任何东西会响。他把它限定在 simple things 是有道理的 —— 一旦你把真正的不变量放进来, 它就变成一句没人验证的承诺。
第四档
没人拦 规则还写在文档里、还挂在嘴上,但两侧代码都不做这件事了。这一档在图上根本看不见。
于是 AI 项目的熵可以定义得很具体:
不是「代码变乱了」,而是 —— 有多少不变量住在第三、第四档,以及它们向下掉的时候有没有人知道。

传统项目里这个问题不存在:不变量只有一种住处(代码),掉下去会炸,编译器就是棘轮。 DDD 能控熵,靠的正是把模型显式化之后交给类型系统去执行。 提示词没有类型系统 —— 所以 DDD 画完图,AI 那一半仍然是无人区。

五一个反直觉的发现:哨兵不能对着 git

看上面第三块。同样的哨兵,对着 git HEAD 跑,漏掉了漂移二。

原因:HEAD 里的 investigate.js 根本没有 cui_bono —— 那个字段是加在工作区里的,一直没提交。查一下就知道有多久:

investigate.js 上一次提交是 08-29 19:49,到今晚已经 2 天 1 小时。 而它每跑一轮侦查要驱动 22 个 agent。

也就是说:这两天真正在生产的那份代码,git 里一直没有。 传统项目里这不可能 —— 你没法把未提交的代码部署到线上。 但 LLM 侧是「改完立刻生效」的:~/.claude/ 下的文件保存即上线, 没有构建、没有部署、没有 PR,连 git status 都要你自己想起来去看。

结论:AI 项目的检查必须对准「此刻真正在跑的那份」,不是仓库里那份。 这也解释了为什么这三次漂移全都能活好几天 —— 代码评审看的是 diff,而这些文件根本没进过 diff。

六棘轮怎么才不打滑

Hashimoto 那句话的力量在「never again」:它要求每次犯错都留下一个不可逆的机制。 但棘轮只有卡得住才叫棘轮。上面三次漂移说明这条产线的棘轮打滑了三次,而滑法完全一样 —— 在 代码/提示词 的边界一侧改了东西,另一侧没有任何人在看。

所以对 AI 项目,我会把控熵收敛成三条,顺序不能换:

  1. 先问「这条不变量住在第几档」,再问「它对不对」。 一条住在第三档的正确规则,比一条住在第一档的粗糙规则更危险 —— 后者会炸给你看,前者会安静地烂掉。
  2. 发现漂移时,交付物不是更好的提示词,是一道让它不能再无声重演的检查。 这就是把第三档的东西往上抬到第一档。上面四道哨兵每一道都是这么来的 —— 它们本身是代码,所以它们不会悄悄失效。
  3. 检查对准运行态,不对准仓库。见上一节;这一条是这次真跑之后才发现的, 不跑就想不到。
顺带说一件我自己踩的:哨兵写错了也会骗人。
第一版第三道哨兵对着修好的代码报了一次假警 —— 它把我自己写的说明句 「那道闸门 #155 已经删了」当成了新的承诺,因为排除词里有「已删」却没有「删了」。 一道会乱叫的哨兵会被人关掉,那比没有哨兵更糟。所以修完之后我又把三个时间点重跑了一遍, 现在是 4/4 / 1/3 / 2/4 —— 上面那三块就是重跑后的结果。

七我没做的

四道哨兵目前只是 scratchpad 里的一个脚本,没有进仓库、没有接进任何流程。 把它变成常驻检查(比如接进 publish_page 之前、或者每次侦查起跑前跑一遍) 属于新功能,按 no-work-without-approval 我先问你:

一、这四道要不要进仓库?进的话我倾向放 contexts/ 之外的顶层 —— 它检查的是「代码侧和 LLM 侧一不一致」,不属于任何一个限界上下文。
二、要不要在侦查起跑前自动跑一遍?好处是漂移当场暴露; 代价是多一道可能误报的闸,而这条产线刚刚才因为闸门太多被你砍过一轮(#155)。
三、还是维持现状,我每次动到边界时手动跑?

另外那件更大的仍然摆着:让 Schema 和 Python 实体从同一处生成, 从根上消掉漂移二和漂移三 —— 那是结构改动,要先出设计。
