五那么 AI 系统的 DDD 图该怎么画:四条规则

规则一 · 提示词和 Schema 是模型构件,和类一样上图

判据不是「它是不是代码」,是「它跑起来的时候拦不拦得住东西」。 JSON Schema 交给 LLM 之后在 tool-call 层强制、不合规就让模型重试 —— 那是运行时约束,和 dataclass 一个量级。而 FINDINGS 里那句 enum: ['实','实·单方','网','传','假'],就是 FactGrade 本尊。

反过来,画在图上的 Python Fact 现在什么都拦不住 —— 它只被 harvest_flow.py 用到一次,写手根本不经过它。 按这条判据,它在图上该被降格,不是升格。

规则二 · 每条不变量标出「谁来拦」,而且只有四种答案

代码拦 Schema 拦 提示词说说 没人拦

传统 DDD 不需要这一维,因为答案永远是「代码拦」。AI 系统里一条不变量会在这四档之间迁移, 而且迁移的时候不报错:#155 删掉 gate.py,「引语必须是原件子串」这条不变量 从代码拦掉到了提示词说说, 四天没有任何人看见。图上如果标了这一维,那次删除会当场亮红。

规则三 · LLM 参与的边要画成不确定的

经典 DDD 的箭头默认「同样的输入出同样的东西」。这里不是:同一份卷宗跑两遍, 22 个 agent 的产出不一样,定级也可能不一样。 所以合并那一步才要「取最保守定级」—— 那不是业务规则, 那是为不确定性做的防御,专门为 LLM 存在。 图上不区分这两种箭头,读图的人就会以为重跑一遍能得到同一份卷宗。

规则四 · 聚合边界是文件系统,不是进程

dossier/ 被一个 Python 程序和 22 个语言模型并发读写。 经典聚合的承诺是「边界之内一致性由聚合根保证」,这里没有任何一方保证: 438 条记录里有 6 个字段名(cui_bono why_they_did_it evidence url flow angle) 是领域实体压根不认识的,写进去也没人拦。

所以图上那个圆柱不该画成「仓储」,该画成一个共享内核,而且它的写入方在两种语言里。

六LLM 在这套系统里同时占了四个 DDD 位置

「该不该进图」不是一个位置的问题 —— 它同时坐在四把椅子上,每把椅子的画法不一样。

DDD 角色在这里具体是谁和传统实现的差别
应用服务 / 用例investigate.js 五阶段 22 个 agent 用例逻辑写成自然语言。不确定,要靠冗余(两镜核查)而不是断言来保证
模型定义(权威)FINDINGS / VERIFY JSON Schema 它才是 Fact 的真身。Python 那份是下游副本,已经漂了 2 个字段
防腐层核查 agent(降级)、写手(把【实·单方】写成「他说」) 用提示词实现的防腐层 —— 会静默失效,而且失效时输出仍然看着正常
领域专家 / 通用语言SKILL.md 392 行教义与清单 通用语言第一次有了可执行的载体。代价是它可以和代码悄悄说不一样的话(事故三)
