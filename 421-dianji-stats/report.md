## 四、这套计数能回答什么，不能回答什么

**怎么记的。** 不是页面里的脚本，是服务器：`frontend/vite.config.js` 的
`recordDocView` 每送出一个在册文档就往后端 `POST /api/docs/views` 记一笔。这个设计有
它的好处——关掉 JavaScript 的读者照样计数，`/p/` 下沙箱里的上传页也照样计数。
同一 IP 对同一页三十分钟内只算一次（`VIEW_DEDUPE_MS`），`HEAD` 不算。

**能回答的只有一件事：每页累计被送出过多少次。** 因为库里就只有累计数和最近一次
时刻两列。于是：

| 问题 | 现有数据能答吗 |
|---|---|
| 哪一页被打开得最多（含机器） | ✅ |
| 上周有多少次、这周有多少次 | ❌ 没有流水 |
| 读者从哪来（搜索 / 直链 / 站内） | ❌ 不记 referer |
| 有多少不重复的人 | ❌ 不记 IP，连散列都不记 |
| 是人还是爬虫 | ❌ 不记 UA；本文的取证是从时刻反推出来的，不是数据本身给的 |
| 他们读完了吗、翻了几段 | ❌ 页面上没有任何埋点 |

**去重窗口还有个小洞**：`seen` 这张表在 Vite 进程的内存里，进程一重启（每次
`deploy.sh`）就清空，紧接着的同一批扫描会被重新计一次。所以上面那些机器扫出来的
数，本身也偏高。

**已删除的文档留着数不走**：`doc_views` 268 行里有 190 行的文档已经不在 manifest
里（合计 358 次）。接口按 manifest 过滤，所以看不见；库里一直躺着。

## 五、要真能统计点击，缺的是三件事

以下**没有实现**——派工明说不许改这个应用自己的代码（后端、前端源码、构建脚本），
所以只落成方案，并指出改哪里。

1. **一张流水表**（`doc_view_events`：`doc_id, at, ip_hash, ua_class, referer_host`）。
   写入点就一个，是现成的 `recordDocView`，它此刻已经拿着 `req`，什么都不缺。
   有了流水，上表里六个 ❌ 会变成五个 ✅。IP 存加盐散列即可，不必存原值。
2. **认出爬虫**。UA 落到 `googlebot / bingbot / 其他 bot / 浏览器` 四档，
   分开计数、不要相减。否则爬虫一来，这张表又会像今天一样自己骗自己。
3. **把我们自己排除掉**。上架与验收的请求带一个约定的头（或就按本机来源判定），
   记流水但标 `internal`。**本轮 330 次里估计有三百二十余次会落进这一档。**

第 1、2 两件都在 `recordDocView` 一处；第 3 件需要后端加一张表和一个写接口
（`server/src/main/java/com/kanban/docs/`）。三件都做完之前，「典籍点击量」这个词
只能指「页面被送出的次数」，不能指读者。

## 六、从今天起能看见增长

累计数看不出增长，所以仪表板做了两层：

- **基线差**：页面里钉着 2026-09-17 02:41 的那一份数，每格旁边用红字标
  「自基线 +N」。新增的是谁、涨在哪一本、哪个读本，一眼可见。
- **逐日序列**：每天第一次打开这个页面时，把当天总数记进浏览器的 `localStorage`，
  于是日子一久就长出真正的时间序列（日期 / 累计 / 当日增量）。不改后端一行代码，
  代价是只存在你这台机器的这个浏览器里。

两层都只是权宜。真正的解法是第五节的第 1 件。
